## 1. 目标与范围

### 1.1 目标场景

一批账号（当前 8 个档案，3 个不同 `data_dir`）**长期同时挂机**，每个账号跑相同或不同的 group 任务。
需要一个程序统一下发指令、监控状态、分开看日志。

### 1.2 功能需求

| # | 需求 | 验收标准 |
|---|---|---|
| F1 | 托管 N 个 bot 会话 | 一次启动 8 个账号，互不影响；可单独启停/重登 |
| F2 | 给单个 bot 下发指令 | 指令语法与 TUI **完全一致**（同一份代码） |
| F3 | 批量下发 / 广播 | `@all <cmd>`、`@<服名> <cmd>` 一次命中多个会话 |
| F4 | 查看指定 bot 状态 | 不用手敲 `view`，UI 直接显示与 TUI 侧边栏同字段的实时状态 |
| F5 | 单独查看某个 bot 日志/进度 | 按会话分离的日志流 + 中文页签过滤 |
| F6 | **智能提示**（重点） | 补全 / 帮助 / 参数提示与 TUI **完全一致**，含 NPC「oid -- 中文名」这类动态候选 |
| F7 | 崩溃自动拉起 | 会话崩溃 → 退避重启；密码可用内存或落盘两种模式 |

### 1.3 非目标

- 不做游戏逻辑（属于 `openstory-bot`）
- 不做多机 / 远程控制
- 不做 Web UI
- 不做"每个账号不同 group 的自动分派"（不同就手动单独下发）

### 1.4 产品定位与长期走向

**不存在"TUI 产品"与"manager 产品"，只有一个程序、两种启动形态。**

```
openstory-console.exe --profile <档案>          → 单账号（等同于今天的 TUI 体验）
openstory-console.exe                           → 多账号（档案多选屏 → N 个会话）
openstory-console.exe --profiles a b c          → 显式指定多账号
openstory-console.exe --autorun <group>         → 启动即给全部会话开同一功能组
```

没有"TUI 模式 / manager 模式"之分，只有"这次开几个账号"。

**为什么最终要收口成一个入口（核心动机）**

> 后端功能每新增一次（新指令、新状态字段、新中文渲染规则），**多一个前端就多一套回归测试**。
> 这是长期成本，且随功能数量线性增长——得不偿失。

因此去重不是审美问题，是**降低每次迭代的验证面积**。

**TUI 的去留时间表**（阶段 7 已执行，见 §6.7）

| 阶段 | `crates/tui` 的角色 |
|---|---|
| 1–3 | **回归基准**（不可删除）—— 拆全局、补全表改造、抽 `console` 全靠它验证 |
| 4 | **等价性验收对象** —— "单档启动结果逐项等于今天的 TUI"在此被证明 |
| 5–6 | **只读参照** —— 多会话 UI 开发时的行为字典 |
| 7 | **删除 `crates/tui`**，入口并入统一程序 `openstory-console` |
| 9 之后 | 已执行：目录改名 `crates/tui` → `crates/console`（包名 `openstory-console`），共享层让位为 `crates/console-lib` |

**兼容性要求**：现有入口形态 `openstory-tui --ip ... --account ... --password ...`
继续可用 —— 通过**同一份源码编出的第二个二进制** `openstory-tui.exe` 保证
（见 §6.7），不是转发脚本。

**项目终局定位**：本计划产出的是**本地运行的最终形态**；远期另有**服务器部署形态**（浏览器 + WebSocket 操作）。该方向不改变本计划的任何选择，但有一条必须遵守的架构约束——见 §11.5。

### 1.5 已锁定的设计决定

| 编号 | 决定 | 理由 |
|---|---|---|
| **D1** | **in-process 多会话**：一个进程内跑 N 个 `runtime::run` 任务，不做子进程、不做 IPC | 见 §2.1 |
| **D2** | **单一可执行文件**：单开/多开共用一套 UI 代码。开发期沿用旧名 `openstory-tui`（兼容现有命令），阶段 9 更名为 `openstory-console`；旧名保留为**同源码的第二个二进制**（见 §6.7） | 唯一能真正做到"UI 与交互完全统一"的方式 |
| **D3** | **游戏页面（选人 / NPC 选项 / 商店 / 背包）保留**，作用于**当前选中会话** | 功能不减，只增加"作用于谁"这个维度 |
| **D4** | **密码两种模式都实现**，配置开关：内存态（重启需重填） / 落盘态（重启也能拉起） | 默认内存态；开启自动拉起的档案才需要落盘 |
| **D5** | **补全表数据驱动改造**（`ArgSpec`）+ 解析器一致性测试 + 帮助文本自动生成 | 一次性消灭"补全表与解析器漂移" |

## 2. 架构

### 2.1 为什么 in-process（决策依据摘要）

**代码实测结论：库已经为此准备好了。**

| 维度 | 实测结果 |
|---|---|
| `BotState` | 已是 `Arc<Mutex<BotState>>`，每会话一份 —— **TUI 已经这么用** |
| `Config` | 每会话一份，`runtime::run(config, &mut rx, state)` 按值收 |
| 命令通道 | 每会话一个 `mpsc::Receiver` —— **TUI 已经这么用** |
| 网络连接 | 每个 bot 自己的 TCP，天然隔离 |
| `std::process::exit` | 仅 2 处，都在 `main.rs`，**不在库代码** |
| `unwrap/expect` | 249 处中绝大多数在 `#[cfg(test)]`；生产代码少数几处均有前置检查守卫 |
| **进程级全局状态** | **只有 3 个**（见 §2.3），且都是局部手术 |

**对照进程 + IPC 方案**：in-process 净删掉整个协议层、管道层、序列化层、背压处理、stdout 污染防护、连接就绪重试；且 F4/F6 变成零成本（直接读 `BotState` / 直接复用补全引擎）。
唯一损失是崩溃域合并——而 `tokio::spawn` 本身已隔离 panic（任务 panic 不杀进程），生产代码无 `abort`/`exit`，实际风险很低。

### 2.2 进程与线程布局

```
openstory-console.exe   (旧名 openstory-tui.exe 是同一份源码的第二个二进制)
│
├─ 主线程
│   ├─ 档案选择屏（新建 / 复制 / 删除 / 多选；复用 console::profiles）
│   ├─ 密码输入（批量同服同密码 / 逐个填）
│   └─ 构造 N 个 Session，塞进 tokio runtime
│
├─ tokio multi-thread runtime
│   └─ Session × N
│        ├─ task A: runtime::run(config, &mut cmd_rx, state)   ← 每会话一个 bot 一生
│        ├─ task B: 状态快照/会话控制（重登、停止、拉起）
│        └─ (无 IPC，无子进程)
│
└─ 渲染线程（crossterm + ratatui）
    ├─ 左栏：账号列表（● 在线 / ○ 离线 / 阶段 / Lv / HP 条）
    ├─ 中部：日志页签（13 个中文分类）+ 折行日志
    ├─ 右侧：选中会话详情（与 TUI 侧边栏同字段）
    ├─ F2 看板页：N 个账号 × 全字段表格
    └─ 底部：输入栏 + 补全下拉 + 提示行
```

### 2.3 必须拆掉的三个进程级全局（G1/G2/G3）

| # | 位置 | 问题 | 修法 | 规模 |
|---|---|---|---|---|
| **G1** | `src/emit.rs:158` `static EMITTER: OnceLock<Arc<dyn Emitter>>` | 只能注册一个 emitter → N 个会话的事件全灌进同一日志流 | **task-local 覆盖层**：每个会话的 `runtime::run` 跑在独立 task 内，用 `SESSION_EMITTER.scope(handle, ...)` 包裹；`emit_event()` 先查 task-local，再回退全局。**所有 `emit!` / `emit_f!` 调用点零改动** | ~30 行 |
| **G2** | `src/runtime_config.rs:18` `static ACTIVE_PATHS: RwLock<Vec<PathBuf>>` | N 个账号共用一套 config 路径 → A 的 `reload` 读到 B 的档案，`hunt save` 写错文件 | 新增 `SessionCtx { paths: Vec<PathBuf> }`，`runtime::run` 多收一个参数；`RuntimeConfig::load()` → `load_from(&ctx.paths)`。保留全局作单开兜底 | ~60–100 行 |
| **G3** | `src/names.rs:17-24` 六个 `RwLock<Option<HashMap>>` + `CURRENT_DIR` | `reload_if_needed(dir)` 会**整表替换**；本机 8 档案含 3 个 `data_dir`（`server_a`/`server_c`/`server_b`）→ 两个 bot 交替渲染时**中文名每帧闪烁** | 改为按 `data_dir` 缓存的 `OnceLock<Mutex<HashMap<String, Arc<NameTable>>>>`；`SessionNames` 每会话持一份 `Arc`；`names::*` 增加带 `&NameTable` 的版本，旧签名转发到"当前会话"以兼容 | ~100 行 |

**天生干净、不需改动**：`exptable`（常量）、`packet::TIME_BASELINE`（进程级时间基准，语义正确）、每会话的 `BotState` / `Config` / 命令通道 / TCP 连接。

## 3. 智能提示体系（F6 详细设计）

### 3.1 现状盘点

补全引擎 `completion.rs` 的能力：

- **一级**：命令名 + 别名（`cc` → 补出 `channel`）
- **二级**：静态子命令表（`hunt ` → `on/off/attack/...`）
- **三级（动态）**：来自 `BotState` 的实时候选
  - `npc ` → `npc 100001 -- 米娅`（oid + 中文 NPC 名）
  - `attack ` → 当前地图怪物 oid
  - `warp ` / `move ` / `movewarp ` → `in00 -- 射手村东部`（传送点名 + 目标地图中文名）
  - `rule open ` / `task run ` / `group run ` → 配置里的 id 列表
- 候选可带描述（`-- 中文名`），选中后**只把 `cmd` 填进输入框**，描述不进指令

### 3.2 具体问题：表与解析器是两份手工真相

`COMMANDS`（`completion.rs:32-83`）与 `src/command/parse.rs` 各维护一份，已存在漂移（例如 `group` 的子命令表与 `docs/GUIDE.md`、`parse.rs` 三者措辞不一致）。
另：`sub_or_dyn()` 是逐命令手写 `match`，新增命令需同时改 3 处。

### 3.3 改造方案

**(a) 规格表加入参数类型**

```rust
pub struct CmdSpec {
    pub name:    &'static str,
    pub aliases: &'static [&'static str],
    pub usage:   &'static str,
    pub subs:    &'static [SubSpec],
    pub arg:     ArgSpec,
}

pub enum ArgSpec {
    None, Free,
    Items { tab: Option<u8> }, Skills, MapId,
    MobOid, ReactorOid, NpcOid, Portal,
    RuleId, TaskId, GroupId,
}
```

`sub_or_dyn` 里的逐命令 `match` 被 `dynamic_candidates(arg, prefix, ctx)` 取代 → **新增命令只改 1 处**。

**(b) 解析器一致性测试（把两份真相焊成一份）**

```rust
// crates/console/tests/spec_matches_parser.rs
#[test]
fn every_declared_subcommand_is_accepted_by_the_parser() {
    for spec in COMMANDS {
        for sub in spec.subs {
            let line = format!("{} {}", spec.name, sub.name);
            assert!(openstory_bot::command::parse(&line).is_ok(),
                "补全表宣称支持 `{line}`，解析器却拒绝 —— 表与解析器漂移");
        }
        for a in spec.aliases { /* 同样验证 */ }
    }
}
```

**(c) 帮助文本从同一份表生成** → F1 帮助永远最新，且多开模式不需第二份。

### 3.4 新增指令时各层成本

| 层 | 需要改什么 | 多开控制台侧成本 |
|---|---|---|
| 补全候选 | 加一条 `CmdSpec` | **0**（同一份代码） |
| 帮助文本 | 无（自动生成） | **0** |
| 中文渲染 | 新 tag 时 `zh.rs` 加规则；带 `Field` 语义键则常常无需改动 | **0**（同一份代码） |
| 状态面板 | `snapshot.rs` 加字段 | **0**（同一 struct） |
| UI 交互 | 无 | **0**（同一份代码） |

**结论：在 D1+D2+D5 之下，TUI 新增指令对多开控制台的适配成本为 0。**

## 5. 崩溃自动拉起（F7）

### 5.1 检测

- 会话 task 的 `JoinHandle` 返回 `Err(JoinError)` 且 `is_panic()` → 判定崩溃
- `RunOutcome::Failed`（登录失败/重连耗尽）→ 判定为**认证/环境问题**，不自动拉起（避免密码错导致风暴），标记为「需人工」
- `RunOutcome::Quit` / `DurationElapsed` → 正常结束，不拉起

### 5.2 拉起策略


### 6.5 阶段 8：手动启停（管理器模式）

**动机**：`--profiles a.json b.json` 的语义是"这些号现在就挂上去干活"——启动即
并发登录全部账号。但用户对"管理多个 bot"的预期是**挂上账号、由我决定谁连**。
原计划 §F1 写的就是"可单独启停/重登"，实现时只做了 F3 重启（对已在跑的号），
**漏掉了"启动一个没启动的会话"** —— 于是它严格说不是管理器，而是多开会话台。

| 能力 | 接口 |
|---|---|
| 挂上但不登录 | `--no-autostart`（别名 `--manual`） |
| 只自动启动点名的 | `--start <档案名...>` |
| 启停当前账号 | `F4`（没在跑就启动，在跑就停掉） |
| 启停指令 | `start` / `stop`（当前选中）、`@all start` / `@<前缀> stop`（批量） |

**四个必须想清楚的点**（都是实现时真踩到的）：

| 点 | 处理 | 不这么做会怎样 |
|---|---|---|
| **"手动停" 必须与 "用户 quit" 分开** | `ExitKind::Manual` 独占一档；`Watcher::reset`（F3 走的路径）**不**清掉它 | 手动停掉的号，在 bot 报"连接已关闭"时被退避排定拉起——5 秒后自己醒过来 |
| **"启动失败" 不是 "从未启动"** | `BotSession::start_failed` 单独记；`is_settled()` 把它算"静了" | 用户按一次失败的 start，`has_never_started()` 永远为真 → `all_done` 永不置位 → **程序再也不退出** |
| **`STAGE_RUNNING` 一词两义** | 加 `stopping` 闩：stop 之后、task 收尾之前不许再启动 | 用户 stop 完立刻 start，同一账号同时挂两个登录尝试，服务器踢掉先来的那个 |
| **退出条件必须按"真的会启动几个"起算** | `attach_sessions(.., started)` 显式传入；`live_count()` 只数"还会自己动"的会话 | 手动模式下 `keepalive` 从 2 起算而实际 0 个在跑 → 永不退出；或反过来重连到一半就退出 |

**按下 `F4` 却没有密码时**：**报错**并在左栏亮 `✕ 启动失败 — 需人工`，不静默失败。
手动模式启动时也**不**排队追问密码——那些号现在不登录，问密码是"一上来就全部
登录"的思路，与手动模式相反。

### 6.6 阶段 9：选择屏多选 + 运行时增删账号

**动机**（用户原话）："bash 启动允许输入 profiles，然后启动的时候初始界面是选择
profiles 的界面……那为什么就不能在 profiles 选择要登录的账户，然后进去之后默认是
未启动的……还有就是能否通过命令临时增加新账户进来。当前最主要的问题就是没有体现
管理的感觉。"

三个问题一次解决：

| 问题 | 做法 |
|---|---|
| 入口重复（命令行 `--profiles` vs 选择屏） | **选择屏成为管理器入口**：`Space` 勾选多个 → `Enter` 进去即多开，全部停在「未启动」。`--profiles` 保留给脚本（语义 = 现在就登录） |
| 增删账号要重启 | `profiles list` / `profiles add <路径>` / `profiles remove <档案名>` |
| 勾选与单选混淆 | `PickOutcome::{One, Many}` **分开返回** —— 单选进去连上，多选进去挂上不连。合成一个返回值前端就没法区分这两种意图 |

**取舍记录**：

| 决定 | 理由 |
|---|---|
| 勾选多个 = **不自动登录** | "我挑了这几个号"与"这几个号现在就登录"是两件事。勾 5 个就并发登 5 个，既会撞服务器限制，也不是"管理"该有的样子 |
| `profiles add` **必须能读出配置** | 挂一个永远启动不了的会话是纯噪音。读不出来就拒绝，并说明原因 |
| `profiles remove` **只允许摘不在跑的** | 摘掉正在跑的会话 = bot task 变孤儿继续跑，而界面上再也看不到它，用户无从停止。错误信息直接告诉他"先 stop" |
| 增删之后 `synced = None` | 下标全体前移；不作废的话日志缓存会把**另一个**账号的日志当成当前账号继续显示（最难查的一类错） |
| `rxs` 与 `sessions` 同序增删 | 错位会把某个会话的接收端交给另一个，指令静默发到错误账号 |
| `ArgSpec::Path` 补全列 `profiles/<名>.json` | 这一格要的是**文件路径**，补个裸名字用户还得自己加目录和扩展名 |
| 光标 `▶` 与勾选 `[✓]` 分开渲染 | 光标决定 `N`/`C`/`D` 作用在谁身上；勾选决定 `Enter` 带谁进去。混成一个则"选了几个号"会随手漂走 |

| 二进制 | 新增 `openstory-console.exe`；**保留** `openstory-tui.exe` 兼容入口 |
| 代码 | `openstory_console::` → `openstory_console_lib::`（6 个文件）；文档/注释里的路径与名字同步 |
| 测试 | 940 项全绿；两个二进制入口都实测可用 |

**兼容入口为什么不是转发脚本**：`openstory-tui.exe` 与 `openstory-console.exe`
由**同一份 `src/main.rs`** 编出（`Cargo.toml` 里两条 `[[bin]]`）。转发
（`Command` 拉起新 exe）会多一个进程、退出码与 Ctrl+C 要额外传递，而且一旦
`openstory-console.exe` 被改名或挪走就**静默失效**。同源码还有个附带好处：
两个入口的行为由编译器保证一致，不会出现"新入口修了、旧入口还是老的"。

**代价**：cargo 会对共享的 `main.rs` 打一条提示性 warning
（`found to be present in multiple build targets`）—— 仅提示，构建正常。
不想看到它就删掉 `[[bin]] openstory-tui` 那一段，兼容入口随之消失。

### 6.8 阶段 10：修掉"按回车没反应"（多开 + 手动模式卡在向导）

**现场**（用户实测）：选择屏勾选 2 个账号 → 进控制台 → 弹出登录向导（账号已预填、
密码为空）→ 输入密码 → **按回车毫无反应**，向导永远停在那里。

**复现**：用合成按键驱动真实程序（选择屏 `Space`/`↓`/`Space`/`Enter` → 向导输入
任意密码/`Enter`），`向导仍在 = True`，`连接数 = 0` —— 与现场一致。

**根因（两层，缺一不可）**：

| 层 | 问题 |
|---|---|
| `main.rs` | `interactive = account.is_empty() \|\| password.is_empty()`。多开 + 手动模式不给密码 → 必然为空 → **启动就弹向导**。而手动模式下一个号都没登录 |
| `App::poll_events` | `attach_sessions` 把 `stage_flag` 指向**选中会话自己的** stage（单会话缓冲视图那一套）。会话停在 `WIZARD`（未启动）→ 每帧把主线程刚设好的 `STAGE_RUNNING` **覆盖回 `WIZARD`** → 向导永远关不掉 |

加临时日志确认过：主线程**确实**收到了向导结果、也确实置了 `RUNNING`
（`[DBG] 主线程收到向导结果 account=100000001` / `启动 0 个, autostart=false`），
是渲染线程每帧把它改回去的。所以这不是"按键丢了"，而是"状态被覆盖"。

**修法**：

1. `poll_events` 在**多会话模式**下不再用 `stage_flag` 覆盖 `App.stage` —— 多开时
   `App.stage` 由主线程直接管理。这条同时保护任何"多开 + 会话未运行"的组合。
2. 多开**根本不弹**向导：凭据来自各自的档案/凭据存储，一个全局账号密码框在语义上
   就是错的（也不可能对所有号都对）。判据抽成纯函数 `needs_login_wizard()` 便于直测。
   缺凭据的会话按 `F4` 启动时在**它自己的日志**里报"没有可用密码"，左栏亮
   「启动失败 — 需人工」—— 这才是多开下正确的反馈方式。

**顺带**：向导提示里加一行"输入法开着时 Enter 会被它吃掉 —— 切到英文再按, 或按
`Ctrl+M`"，并真的支持了 `Ctrl+M`。中文输入法用 Enter 上屏候选词，向导里摸不着头脑
的用户需要一个替代路径。

**这一课**：`stage_flag` 在单会话里是"App 的阶段"，在多会话里是"选中会话的阶段"。
同一个字段两种含义，写的时候都对，**放在一起就错** —— 而它只在"多开 + 会话未运行"
这个交集里发作，正是手动模式引入的新状态。

### 6.9 阶段 11：修掉状态面板闪烁

**现场**（用户实测）：登录成功之后右侧状态面板"大概 100ms 闪一下"，参数看着很怪。

**根因**：`App::sync_from_selected` 里这一句

```rust
self.snap = self.state.try_lock()
    .map(|st| Snapshot::from(&*st))
    .unwrap_or_default();      // ← 拿不到锁就塞一个「全 0 快照」
```

- 这句**每帧**都跑（多会话下 `poll_events` 每帧调 `sync_from_selected`）。
- 而 bot 在 `runtime.rs` 的 tick 分支里**持锁**调 `command::tick` —— 里面有网络
  I/O，可能几十上百毫秒。
- 那几帧渲染线程 `try_lock` 失败 → 右侧面板被塞进全 0 快照显示一帧 → 下一帧恢复。

用户看到的"闪烁"就是**全 0**（等级 0、金币 0、血量 0/0）与真实数据交替。

**修法**：只在**真的换了会话**时立即刷快照（那时锁失败也不能拿旧账号的数据），
其余每帧交给 `poll_events` 已有的 `try_lock` —— **失败就保留上一份好数据**。
"拿不到锁" 永远不该等于 "数据是 0"。

**为什么之前一直没发现**：`sync_from_selected` 只在多会话下才被每帧调用，而多开是
阶段 5 才有的。单会话时代这条路径不跑，所以从没暴露。

**回归测试**：`a_busy_session_does_not_blank_the_status_panel` —— 手动占住会话的
状态锁，跑 3 帧，断言面板仍持有上一份真实数据。**已验证它在修复前会失败**
（把 `if changed_session` 改回 `if true` 就红），不是一条"永远为真"的假测试。

### 6.10 阶段 12：按键日志（诊断手段）

"按键没反应"这类问题**没法靠读代码定位** —— 得先知道键到底有没有到这个进程。
新增 `OPENSTORY_KEYLOG=<路径>` 环境变量：开启后把每个按键与当时的阶段追加写进文件。

三种情况一眼可分：

| 文件里的情况 | 结论 |
|---|---|
| **没有那一条** | 键没到进程（输入法吞了 / 终端抢了 / 窗口没焦点） |
| 有，但 key 是别的码 | 终端把它报成了别的键 |
| 有，key 也对，但没有后续行为 | 状态机 / 处理逻辑的问题 |

刻意**不记字符内容**（只记"这是一个字符键"）—— 否则密码会被写进诊断文件。

### 6.3 多会话键位定案（阶段 5 落地，阶段 6 增补）

| 键 | 作用 | 为什么是它 |
|---|---|---|
| `Alt+↑↓` | 切换选中会话（循环） | **不能用 `Ctrl+↑↓`**：Windows Terminal 拿它切自己的标签页，按键根本到不了程序。`Alt+↑↓` 不与 `↑↓`（输入历史/补全轮换）冲突 |
| `F2` | 看板页（N 行 × 全字段） | 只在多会话（`session_position().1 > 1`）下生效，单档按 F2 版面不变 |
| `F3` | 手动重启选中会话 | **不能用 `R`**：运行阶段普通字符都要进输入框，抢一个字母会让 `chat ...` 里的大写 `R` 打不出来。运行阶段与"已结束"阶段都挂了它 —— 恰恰是结束后最需要手动拉起 |
| `F4` | **启动 / 停止**选中会话（阶段 8） | 手动模式下的常用操作就是这两件，一个键管完。**不用 `S`**：`s` 是拼音输入里出现频率极高的字母（shang / sha / …），抢掉它等于让用户打不出字。与 `F3` 的分工：`F3` = 重启（清退避计数后立刻拉起），`F4` = 启停 |
| `@all` / `@<前缀>` | 批量下发 | 前缀无命中时报错而**不是**退化发给当前选中会话（最危险的静默行为） |
| `@all start` / `@<前缀> stop` | 批量启停（阶段 8） | 与批量下发同一套目标语法。`start` / `stop` 是**控制台内建指令**, 拦在 `App::submit` 里、不发给 bot（bot 不认识这两个词） |

### 6.4 密码双模式（已实现）

自动拉起要重建会话就需要**明文密码**在手（核心层每次重连都要重新登录），而
核心层的硬纪律是"密码永不落盘"。两者的调和方式：

| 模式 | 开关 | 行为 |
|---|---|---|
| 内存态（**默认**） | 无 / `--no-remember-password` | 密码只在本次进程内。与今天一字不差 |
| 落盘态 | `--remember-password` | 写到 `profiles/.manager.json`，让自动拉起跨程序重启生效 |

* 两个开关都给时**不记优先**（保守的一侧必须赢 —— 脚本拼接很容易同时带上两个）
* 明文，**不做假加密**：假加密的解码脚本就在旁边，只会让人误以为安全。文件里
  写了一条 `warning` 字段说明它是明文
* Unix 显式 `0600`（目录里的 `0644` 会被同机其它用户读到）；Windows 依赖用户
  目录 ACL。`.gitignore` 已排除该文件
* 密码优先级：**档案里的 `login.password`（用户自己写的）> 凭据存储**；
  存储里没有时**不清空**模板里已有的密码
* 按**档案名**索引而不是账号名：同一个账号在两个档案里可以是不同密码
  （不同服 / 不同 key），按账号索引会取错
* 启动时逐档检查缺密码的档案并问一次（`--password` / stdin 非终端时自动跳过，
  不阻塞自动化）；留空 = 跳过该档，Esc = 全部跳过

**阶段 1–2 期间修掉的真实 bug（备查）**
1. `names::reload_if_needed` 整表替换 → 多 data_dir 并存时中文名会闪错（本机 8 档案横跨 3 个目录，必然触发）
2. `hunt save` 写回目标来自进程全局 → A 账号会把设置写进 B 的档案
3. TUI 渲染层读进程默认名字表，而默认表晚一步才设置 → 连接前几帧地图名显示「未知」
4. `names::force_reload` 用 `OnceLock` → 语义上无法真正重载
5. 畸形名字表 JSON 被静默吞掉 → 全部显示「未知」且无线索（现在打 stderr）
6. TUI 帮助/补全表比解析器**严**：`task stop`、`group open/close/status`、`view eqpinfo`、`view portals`、`sell tab`、`buff cancel`、`cashshop buy/get/store/out` 全补不出来
7. TUI 帮助/补全表比解析器**松**：`group start`、`group cancel`、裸 `hunt filter add/del`、单参数 `buy`/`keymap set`/`skill cast`/`setvar` —— 补出来敲下去必然报错
8. `parse.rs` 的 `buy` 要求 `itemid` 与 `qty` 都在，但 usage 字样写着 `[qty]`（以解析器为准，已在表里标注）

**阶段 6 期间修掉的真实 bug（备查）**

9. `EventQueue::emit` 用 `lock().unwrap()` → bot panic 毒化这把锁，**下一次**
   emit 跟着 panic → 二次 panic → **整个进程 abort**。多开时一个号崩了带走
   全部号（多开最不能接受的失败模式）
10. `BotSession::outcome()` 用 `.ok()` → 毒化的锁被读成"没有结束原因"，而写入
    侧是容错的，于是"写了但读不到"。两侧容错策略必须一致
11. 触发过的等待窗口不收尾 → 会话被拉起后**正常退出**时状态一直停在"在等
    重连" → 退出计数永不为 0 → 主线程不肯退出，UI 也一直显示不会发生的倒计时
12. 尝试次数存在"会被清掉的等待窗口"里 → 每次拉起都从 5 秒重来，
    "最多 3 次然后放弃"永远达不成（那是重连风暴）
13. 待触发的窗口没有过期机制 → 调用方拿了 token 却没 spawn 时，那个窗口会
    **永久**挡住后续掉线（会话卡在"准备重连"里什么都不会发生）
14. `needs_attention` 只认"已放弃"和"登录失败" → **拉不起来**的会话显示成普通
    "○ 已结束 — 未连接"，和用户自己 quit 一模一样。那是最危险的一种静默
15. F3 分支加进了 `on_key` 的"已结束" match 分支而不是 `on_input_key` →
    会话**还在跑或刚掉线正等退避**时按 F3 完全没反应（而那正是最需要它的场合）
16. 日志 `Filter` 是全局一个字段 → 在 A 上切到"聊天"，切到 B 也变成"聊天"，
    而 B 的日志根本没被看过（用户会以为 B 没有日志）


**阶段 1–4 的硬纪律（保证回归基准有效）**

> 在这四个阶段里，**TUI 的行为是"只读"的**。发现不合理的地方（快捷键、文案、布局、补全顺序…）一律**记进 TODO，不要顺手改**。
> 原因：一旦改了，就无法判断后续多会话模式下的行为差异是"新引入的 bug"还是"当初顺手改的"。等阶段 5 之后统一在唯一一份代码里改，改一次两边都对。

## 11.5 项目终局形态（远期方向，本计划不实现）

> 记录于此的目的**不是现在开工**，而是确保本计划的架构选择**不会堵死这条路**。

### 三种形态，三个终点

| 形态 | 前端 | 部署 | 定位 |
|---|---|---|---|
| **单开** | TUI | 本地 | 开发期基准 / 快速单账号 |
| **本地多开** | TUI 多会话 | 本地 | **本项目本地运行的最终形态**（本计划产出） |
| **服务器版** | 浏览器（WebSocket 实时推送） | 服务器托管 | **本项目服务器部署的最终形态**，远期目标 |

明确不做：
- **不开发复杂的独立客户端**（不做 Electron / 桌面 GUI / 原生 App）
- 服务器版的**客户端复杂度靠"复用游戏 UI 视觉"降低**，靠服务端承担逻辑，而不是靠客户端堆功能

### 服务器版的功能想象

- 浏览器里直接操作登录游戏（不用在终端里点选）
- WebSocket 实时接收 bot 信息（日志流、状态、进度）
- **可复刻游戏 UI 界面**，让操作比 TUI 直观得多

### 现有 Web 层基础

`crates/webui` 已经存在：`tiny_http` 同步 HTTP + 静态 HTML，**纯 config 编辑**（无 WebSocket），已依赖 `openstory-bot` 并复用 `RuntimeConfig` 做保存校验。
即"Web 那半条腿"已经有地基，且走的是"独立进程 + 文件解耦"的模式。

**服务端技术栈（远期待定，届时单独决策）**：

| 路线 | 特点 |
|---|---|
| `tiny_http` + HTMX / 服务端渲染片段 | 与现有 `webui` 一致，复杂度最低，适合"操作型"界面 |
| `axum` + WebSocket + REST | 适合实时推送 + 复刻游戏 UI 的富交互 |

### 对**当前架构**的唯一约束（重要）

服务器版意味着：**同样的"会话"语义要能在远端进程里被驱动**。因此本计划做一条**零成本的预留**：

> **`SessionSet` / `Session` 的公开接口必须做"进程内模拟"友好设计——不依赖同一个进程内的其它会话，不依赖全局单例，可通过 channel 构造。**

具体落实（都在既有工作内，不增加工期）：

| 约束 | 理由 | 成本 |
|---|---|---|
| 会话输入统一走 `mpsc::Receiver<String>`，**不直接跨会话读内存** | 远端实现只需换成"从 WebSocket 收指令" | 0（原本就这么设计） |
| UI 只调 `SessionSet` 的公开方法，**不直接触碰 `run` / 全局** | 远端实现用 RPC 句柄替换本地对象 | 0 |
| `emit::Category` / `Level` / `Field` **加 `Serialize`/`Deserialize`** | 服务器版要推 JSON 事件与快照 | 3 行 derive（已在 G1 相关改动范围内） |
| `Snapshot` 带 `Serialize`/`Deserialize` | 同上 | 0（D5 相关，已规划） |

**不需要现在做的**：不引入 trait 抽象、不提前设计 Web API、不动 `crates/webui`。

> 换句话说：**只要不写"必须同进程"的代码（跨会话直接读内存、全局单例、会话间静态共享可变状态），服务器版就是后续叠加一个前端的事。** 这也正是 G1/G2/G3 要拆的东西——本计划的地基工作**同时**服务于本地多开和未来服务器版。

### 现有分层已验证（实测）

```
grep "use crossterm|use ratatui|stdout()|enable_raw_mode"  src/   →  无匹配
```

**`openstory-bot` 核心层零终端依赖**：`command/`（7 个模块）、`handlers/`、`parsers/`、`runtime`、`state`、`emit`、`names` 全部不含 ratatui/crossterm。
即"底层复用、上层构建"已是**既有结构**，不是需要新建的意图。

| 层 | crate | 依赖 | 状态 |
|---|---|---|---|
| **核心层** | `openstory-bot`（`src/`） | 零 UI 依赖；输出统一走 `emit!` 抽象 | ✅ 已干净 |
| **共享控制台层** | `console`（新建） | ratatui + crossterm + `emit` 类型 | 阶段 3 建立 |
| **前端 A（本地）** | 多开控制台 | `console` + bot 核心 | 阶段 4–6 |
| **前端 B（服务器）** | 未来 Web | **不依赖 `console`**；直接用 bot 核心 + `emit` JSON + `Snapshot` | 远期 |

**推论**：服务器版 = **新增一个不 import ratatui 的前端**，引擎一行不改。

**后续优化点（不在本计划范围）**：`command_spec`（补全 + 帮助的数据源）严格说属于核心层或独立小 crate，因为服务器版同样需要"这条指令怎么用、参数是什么"来生成界面提示。阶段 2 先放进 `console`（那里离消费方最近），等服务器版真正开工时再评估是否上移。
