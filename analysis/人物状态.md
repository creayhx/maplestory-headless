# 冒险岛 人物死亡机制

## 概述

MapleStory 的死亡判断由**服务端驱动**，客户端不做独立死亡判定。服务端计算伤害后通过 **SetStat 包 (Opcode 34)** 下发 HP 值和死亡状态标志，客户端仅做呈现和 UI 反应。本文档梳理本地玩家和远程玩家两条 HP 更新路径，以及死亡触发的关键环节。

---

## 核心结论

**客户端没有"if HP <= 0 then die"的本地死亡检查逻辑。** 死亡完全由服务端通过 SetStat 包中的状态位控制。

| 玩家类型 | HP 更新方式 | 死亡判断方 |
|---------|-------------|-----------|
| 本地玩家 | SetStat 包 (Opcode 34) → `CWvsContext::OnStatChanged` | 服务端 |
| 远程玩家 | HP 专用包 → `CUserRemote::OnReceiveHP` | 服务端 |

---

## 调用链

```
服务端下发HP更新
│
├─ 本地玩家路径 ──────────────────────────────────────────
│  CWvsContext::OnPacket (0xA10CE0)
│    └─ Opcode 34 → CWvsContext::OnStatChanged (0xA292F5)
│          │
│          ├─ CharacterData::DecodeSetStat (0x4F2674)
│          │     └─ 解析各属性值 (HP/MP/EXP等)
│          │           └─ HP字段 → ZtlSecureTear_short_ 加密写入 CharacterData+0x61
│          │
│          └─ 死亡状态位检查 (0xC000000000LL)
│                ├─ 命中 → 触发死亡UI + 复活对话框
│                └─ 未命中 → 正常更新HP显示
│
├─ 远程玩家路径 ──────────────────────────────────────────
│  CUserPool::OnUserRemotePacket
│    └─ CUserRemote::OnReceiveHP (0x991253)
│          │
│          ├─ CInpacket::Decode4 → 当前HP
│          ├─ CInpacket::Decode4 → 最大HP
│          ├─ 计算 100*curHP/maxHP → UserRemote+0x3C9 (HP百分比)
│          ├─ 计算 curHP/maxHP     → UserRemote+0x70F (HP比值)
│          └─ sub_949163 / sub_9EA4E7 → UI刷新
│
└─ 场地HP减少路径 ───────────────────────────────────────
    CUserLocal::OnNotifyHPDecByField (0x967B85)
      └─ CUserLocal::TryConsumePetHP (0x967FF1)
            └─ HP过低时自动使用宠物药水
```

## CharacterData::DecodeSetStat 完整位标志映射 (0x4F2674)

从 SetStat 包中读取 4 字节位标志(int32)，逐位检查并解码对应字段。已确认字段：HP(bit12)、MaxHP(bit13)。

```
入口: this=CharacterData*, a2=CInPacket*
  │
  ├─ flags = CInpacket::Decode4(a2)    ← 读取4字节位标志
  │
  ├─ bit 0 (0x000001): byte,           this+0x12          (直接赋值)
  ├─ bit 1 (0x000002): int32,          this+0x13          (直接赋值)
  ├─ bit 2 (0x000004): int32,          this+0x17          (直接赋值)
  ├─ bit 3 (0x000008): buffer8,        this+0x1B          (DecodeBuffer)
  ├─ bit 4 (0x000010): buffer8,        this+0x23          (DecodeBuffer)
  ├─ bit 5 (0x000020): buffer8,        this+0x2B          (DecodeBuffer)
  │
  ├─ bit 6 (0x000040): byte(加密),     this+0x33→+0x35    (ZtlSecureTear_unsigned_char_)
  ├─ bit 7 (0x000080): short(加密),    this+0x39→+0x3D    (ZtlSecureTear_short_)
  ├─ bit 8 (0x000100): short(加密),    this+0x41→+0x45    (ZtlSecureTear_short_)
  ├─ bit 9 (0x000200): short(加密),    this+0x49→+0x4D    (ZtlSecureTear_short_)
  ├─ bit10 (0x000400): short(加密),    this+0x51→+0x55    (ZtlSecureTear_short_)
  ├─ bit11 (0x000800): short(加密),    this+0x59→+0x5D    (ZtlSecureTear_short_)
  ├─ bit12 (0x001000): short(加密),    this+0x61→+0x65    ← 当前HP ✓
  ├─ bit13 (0x002000): short(加密),    this+0x69→+0x6D    ← 当前MP ✓
  ├─ bit14 (0x004000): short(加密),    this+0x71→+0x75    (ZtlSecureTear_short_)
  ├─ bit15 (0x008000): short(加密),    this+0x79→+0x7D    (ZtlSecureTear_short_)
  ├─ bit16 (0x010000): short(加密),    this+0x81→+0x85    (ZtlSecureTear_short_)
  ├─ bit17 (0x020000): short(加密),    this+0x89→+0x8D    (ZtlSecureTear_short_)
  ├─ bit18 (0x040000): long(加密),     this+0x91→+0x99    (ZtlSecureTear_long_)
  ├─ bit19 (0x080000): short(加密),    this+0x9D→+0xA1    (ZtlSecureTear_short_)
  ├─ bit20 (0x100000): long(加密),     this+0xA5→+0xAD    (ZtlSecureTear_long_)
  └─ bit21 (0x200000): long(加密),     this+0xB1→+0xB9    (ZtlSecureTear_long_)
```

### 加密模式说明

`CharacterData::DecodeSetStat` 使用三种 ZtlSecureTear 变体：

| 加密函数 | 地址 | 适用类型 | 偏移对 |
|---------|------|---------|--------|
| `ZtlSecureTear_unsigned_char_` | 0x4F774D | byte | buf→checksum (间隔2) |
| `ZtlSecureTear_short_` | 0x4F7780 | short | buf→checksum (间隔4) |
| `ZtlSecureTear_long_` | 0x416E36 | long | buf→checksum (间隔8) |

每个加密字段的存储布局：`[buf: 4字节密钥区][checksum: 4字节校验和]`，密钥区存放 XOR 密钥 + 密文。

## CharacterData HP 字段

人物对象中的 HP 字段使用 `ZtlSecureTear_short_` 加密存储，每字段 8 字节（4 字节密钥区 + 4 字节校验和）：

| 字段 | 密钥区偏移 | 校验和偏移 | SetStat 位标志 | 加密方式 |
|------|-----------|-----------|---------------|---------|
| 当前 HP | `this+0x61` | `this+0x65` | bit12 (0x1000) | `ZtlSecureTear_short_` |
| 最大 HP | `this+0x69` | `this+0x6D` | bit13 (0x2000) | `ZtlSecureTear_short_` |

> 加密机制详见 [人物属性-防御力.md](人物属性-防御力.md) 和 [BUFF加密机制.md](BUFF加密机制.md)

## 死亡状态位

在 `CWvsContext::OnStatChanged` (0xA292F5) 的反编译中存在对 `0xC000000000LL` (位38/39) 的状态位检查：

```
OnStatChanged:
  │
  ├─ CharacterData::DecodeSetStat  →  解析属性值
  │
  └─ if (state_flags & 0xC000000000LL):
        │
        ├─ 触发死亡UI (复活对话框弹出)
        ├─ 播放死亡动画
        └─ 禁用操作输入
     else:
        └─ 正常更新HP/MP显示
```

状态位 `0xC000000000LL` 由服务端设置，表示玩家死亡(`bit 38`)或复活(`bit 39`)。

## 不死方案

由于客户端不做独立死亡判定，实现"本地玩家不死亡"需要阻断服务端死亡指令的执行。

### 方案A：Hook OnStatChanged 拦截死亡状态位

在 `CWvsContext::OnStatChanged` (0xA292F5) 中，当检测到死亡状态位 `0xC000000000LL` 时跳过处理。

```
目标: 跳过死亡状态位分支
位置: CWvsContext::OnStatChanged (0xA292F5)
      └─ 状态位检查后的 jz/jnz 跳转
效果: 死亡状态位被忽略，HP 正常更新但死亡UI不触发
```

### 方案B：Hook CharacterData::DecodeSetStat clamp HP

在 `CharacterData::DecodeSetStat` (0x4F2674) 中，bit12(HP) 解析后、加密写入前，将明文值 clamp 到 ≥1。

> **实测：碰怪崩溃。** 可能原因：服务端下发 HP=0 伴随状态位变化时，客户端 HP 被 clamp 到 1，但状态位仍在，后续逻辑路径出现不一致导致崩溃。此方案存疑。

```
目标: HP明文值 clamp 到 ≥1
位置: CharacterData::DecodeSetStat (0x4F2674)
      └─ HP 值(0x4F279A)进入 ZtlSecureTear_short_ 加密之前
效果: 即使服务端下发 HP=0，写入加密缓冲区前被修正为 1
```

### 方案C：NOP 场地HP减少

```
目标: 屏蔽场地类持续扣血
位置: CUserLocal::OnNotifyHPDecByField (0x967B85)
效果: 火焰地带、毒雾等地图机制的HP减少被屏蔽
```

> **注意：** 以上方案仅作用于客户端表现。服务端仍会记录玩家死亡状态，
> 部分操作（如传送、切换地图）可能被服务端拒绝，需配合其他修改。

## CUserRemote::OnReceiveHP 逻辑 (0x991253)

远程玩家 HP 更新包的内部处理流程：

```
CUserRemote::OnReceiveHP(this, packet)
  │
  ├─ curHP = CInpacket::Decode4(packet)    ← 解码当前HP
  ├─ maxHP = CInpacket::Decode4(packet)    ← 解码最大HP
  │
  ├─ this->0x3C9 = 100 * curHP / maxHP      ← HP百分比 (整数)
  ├─ this->0x70F = curHP / maxHP             ← HP比值
  │
  ├─ sub_949163(this)                        ← 更新HP显示
  │
  └─ if (某些条件):
       └─ sub_9EA4E7(this)                  ← 刷新UI组件
```

该函数仅处理**远程玩家**的 HP 更新，本地玩家的 HP 走 SetStat 包路径。

## MP (蓝量) 机制

### 概述

MP 处理逻辑与 HP 类似，均由服务端通过 **SetStat 包**下发。与 HP **根本性差异**：MP **没有本地消耗路径**，客户端不存在类似 `OnNotifyHPDecByField` 的"扣蓝通知"函数。所有 MP 变化（技能消耗、药水恢复、自然恢复）均由服务端计算后通过 SetStat 包下发。

### 数据流

```
服务端决定 MP 变化（技能扣蓝/药水回蓝/自然恢复）
    │
    ▼
SetStat 包 (Opcode 34) → bit13 (0x2000) 携带当前MP
    │
    ▼
CWvsContext::OnStatChanged (0xA292F5)
    │
    ▼
CharacterData::DecodeSetStat (0x4F2674)
    │  bit13 (0x2000) → MP 更新标志 ✓
    │    ├─ CInpacket::Decode2 → 明文 MP 值 (16位有符号)
    │    └─ ZtlSecureTear_short_(明文, this+0x69) → 校验和 → this+0x6D
    │
    ▼
    CharacterData 加密存储 → UI 解密刷新
    ```

    > **MP bit 确认：** bit13 (0x2000) → CharacterData `this+0x69` (缓冲区) / `this+0x6D` (校验和)，采用 `ZtlSecureTear_short_` 加密，与 HP(bit12) 完全相同的加密模式。

### HP vs MP 路径对比

| 对比项 | HP | MP |
|--------|-----|-----|
| 服务端下发 | SetStat bit12 (0x1000) `this+0x61` | SetStat bit13 (0x2000) `this+0x69` ✓ |
| 场地伤害通知 | `CUserLocal::OnNotifyHPDecByField` (opcode 215) | **不存在** |
| 宠物/药水自动 | `CUserLocal::TryConsumePetHP` | **不存在** |

### 蓝量不消耗方案

由于 MP **没有本地消耗路径**，所有 MP 变化全部来自服务端下发，因此实现"蓝量不消耗"只需在 `CharacterData::DecodeSetStat` 中 clamp MP 值。

**核心思路：** 服务端每帧通过 SetStat 包下发当前 MP，我们在客户端改掉这个值再写回加密区，服务端无法察觉。

#### 方案：Hook DecodeSetStat bit13 — 强制 MP 不减

在 `DecodeSetStat` (0x4F2674) 的 bit13 分支中，`CInpacket::Decode2` 读取明文 MP 后、`ZtlSecureTear_short_` 加密前，插入 clamp 逻辑。

**Hook 点定位:**

查找流程同 `人物属性-查找流程.md`，但这里是 CharacterData 而非 BUFF 区：

```
目标: CharacterData::DecodeSetStat (0x4F2674)
bit13 (0x2000) 分支:
  地址 0x4F27AC: call CInpacket::Decode2    ← 从包读取 MP 明文
  地址 0x4F27B3: lea edx, [esi+0x69]        ← MP 加密缓冲区
  地址 0x4F27B6: mov ecx, eax               ← ECX = MP 明文值
  → ★ Hook 点: 在此处替换 ECX，取 max(ECX, 当前MP)
  地址 0x4F27B8: call ZtlSecureTear_short_  ← 加密写入
  地址 0x4F27BD: mov [esi+0x6D], eax        ← 存储校验和
```

**AA 脚本思路:**

```
// 在 mov ecx, eax 处拦截 (0x4F27B6)
// 读取当前已加密存储的 MP (this+0x69 → ZtlSecureFuse 解密)
// 比较: 如果服务端下发的 MP < 当前 MP，则保持当前 MP 不变
// 否则使用服务端下发的值（允许吃药水回蓝）

[ENABLE]
alloc(mp_hook, 256)
alloc(tracked_max_mp, 4)

// 追踪历史最大值，初始化为 0
tracked_max_mp:
dd 0

mp_hook:
  mov ecx, eax               // 原始指令
  push esi
  push ecx
  push ecx                   // arg2: server_mp
  push esi                   // arg1: CharacterData*
  call do_clamp
  add esp, 8
  mov ecx, eax               // ECX = clamped MP
  pop esi
  add esp, 4
  lea edx, [esi+0x69]        // MP 缓冲区
  call 004F7780              // ZtlSecureTear_short_
  jmp 004F27BD               // 回原始 mov [esi+6D],eax

do_clamp:
  push ebp
  mov ebp, esp
  push ebx
  mov ebx, [ebp+0C]          // server_mp
  mov eax, [tracked_max_mp]  // 历史最大值
  cmp ebx, eax
  jle @f                     // server ≤ max → 保持 max
  mov eax, ebx               // server > max → 更新
  mov [tracked_max_mp], eax
@@:
  pop ebx
  pop ebp
  ret

0x4F27B6: jmp mp_hook
0x4F27B6+5: nop

[DISABLE]
0x4F27B6: db 8B C8 E8 BD 4F 00
dealloc(mp_hook)
dealloc(tracked_max_mp)
```

**效果：**
- 技能扣蓝 → 服务端下发减少后的 MP → clamp 保持最大值 → MP 不降
- 吃药回蓝 → 服务端下发增加后的 MP → clamp 通过 → MP 正常上升
- 换图/重登 → 服务端下发新 MP → clamp 通过 → 正常同步

**注意：** 如果服务端有 MP 异常检测（客户端 MP 与服务端计算不一致），此方案可能触发检测。
多数私服不做这种校验，但若遇到可配合发包拦截（拦截扣蓝 Opcode 再回复旧 MP）。
