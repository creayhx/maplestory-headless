# 冒险岛 物品掉落劫持方案

## 基本信息

| 项目 | 内容 |
|------|------|
| 目标进程 | MapleStory.exe (32-bit) |
| 基址 | 0x400000 |
| 目标RVA | 0x10E7C0 → 0x50E7C0 |
| 功能 | 写入物品模板ID到掉落实体+52偏移 |

## 调用链

```
sub_54112E  (主网络包分发器)
  └─ opcode 272 (0x110) → DropItem_Dispatch (0x50E6CF)
       ├─ 272 → DropItem_Create (0x50E6F4)   ← 创建掉落
       └─ 273 → DropItem_Remove (0x50F385)   ← 移除掉落
```

- opcode 272 由 **服务端下发**，客户端收到后创建掉落实体
- opcode 273 同样由服务端下发（玩家拾取或物品超时消失）

---

## 关键分支逻辑

**分支判断点：0x50EA04**

```asm
; 0x50E9F7
mov  [ebp-28h], ebx        ; ebx = 0 (清零计数器)
mov  eax, [ebp-14h]        ; eax = 实体对象指针
cmp  [eax+30h], ebx        ; 比较 实体+48 与 0
mov  byte ptr [ebp-4], 7
jz   loc_50EACC            ; +48==0 → 跳转地面掉落路径
                            ; fall through → 直达背包路径
```

| 实体+48 值 | 路径 | 行为 |
|-----------|------|------|
| 0 | 地面掉落 | 物品展示在地面，需拾取 |
| 非0 | 直达背包 | 仅视觉特效（物品直接"飞入"背包） |

> ⚠ **注意：** "+48非0"的"直达背包"路径仅仅是**客户端渲染路径**，用于任务奖励、商城购买等场景的视觉特效展示。**走这条路径并不会让物品真的进入背包**——物品是否入包由服务端控制。NOP掉`jz`跳转只是改变了客户端渲染方式，实际物品仍然在地上，仍然需要发送拾取包才能拿到。

**服务端对所有普通掉落发 +48=0**，所以全部走地面掉落路径。

### 真正的"自动拾取"实现方式

真正的全捡/自动拾取不能靠改`+48`分支路径实现，必须**循环遍历掉落池，对每个掉落调用拾取发包函数**：

```
遍历 CDropPool 中所有 drop
  └─ 对每个 drop 调用 sub_A126C5(dropId, itemId, ...) 发送 opcode 198 拾取包
  └─ 配合防封延迟
```

详见 [物品捡取距离检测.md](物品捡取距离检测.md) 中的分析。

## Hook 方案

### 方案一：全局 NOP 跳转（❌ 不可行，仅视觉效果）

> ⚠ **这个方案是错误的。** 详见上方关键分支逻辑的说明，"直达背包"路径只是视觉特效渲染，**不会让物品真正进入背包**。正确的实现方式见下方"真正的实现：循环发包捡取"。

直接NOP掉条件跳转，让+48=0的掉落也走直达背包的视觉渲染路径。

**补丁位置：0x50EA04**

```
原始: 0F 84 C2 00 00 00    ; jz near 0x50EACC (6 bytes)
改为: 90 90 90 90 90 90    ; NOP × 6
```

**结果：**
- 所有掉落视觉上"飞入"背包（走直达渲染路径）
- ⚠ **实际上物品并未入包**，仍需正常走拾取流程
- 客户端看不到掉落在场景上（视觉被跳过）

---

### 方案二：按物品ID过滤（❌ 同样不可行）

同上，修改`+48`分支只能影响视觉渲染路径，无法真正实现物品入包。保留此处分析仅作参考。

**代码洞穴内容（示例：仅对装备ID 1402000生效）：**

```asm
; Hook at 0x50EA04 (原 jz 占用6字节, 改为 jmp 到洞穴)
; Cave 地址：找一个可写可执行的内存区域

cmp  dword ptr [eax+34h], 1402000   ; 检查物品ID
jz   loc_50EACC                     ; 匹配 → 走地面掉落（正常渲染）
; 不匹配 → 走直达视觉路径
jmp  直达地址                         ; 计算实际地址
```

---

### 真正的实现：循环发包自动拾取

要实现**真正的自动拾取/全捡**，必须**对掉落池中每个掉落调用拾取发包函数** `sub_A126C5`。服务端收到opcode 198包后验证通过，物品才会真正进入背包。

#### 核心思路

```
遍历 CDropPool 中所有活跃 drop
  └─ 对每个 drop 调用 sub_A126C5(dropId, itemId, dropX, dropY) → 发送 opcode 198
  └─ 每次发包间隔防封延迟（如 50-200ms）
```

#### 参考实现

```cpp
void AutoLootAll(CUserLocal* user) {
    if (!user->dropPool) return;
    if (!CanPickup()) return;

    for (each drop in user->dropPool) {
        // 跳过不可捡状态
        if (drop->state != 3) continue;     // 非可拾取状态
        if (!drop->isPickupable) continue;  // 标记不可捡
        if (drop->ownerType == 0 && drop->ownerId != user->charId) continue;  // 非我所属
        if (drop->ownerType == 1 && drop->ownerId != user->partyId) continue;  // 非我队伍

        // 发送拾取包
        sub_A126C5(user, drop->pos, drop->dropId, drop->itemId);
        Sleep(50); // 防封延迟
    }
}
```

#### 触发方式

- **方案A：** 在按键拾取函数 `sub_50D440` 末尾 Hook，改为遍历全量发包（而非只捡最近的第一个）
- **方案B：** 注入线程/定时器，周期性调用遍历逻辑
- **方案C：** 配合全屏捡取（修改距离检测），详见 [物品捡取距离检测.md](物品捡取距离检测.md)

#### 关键函数

| 函数 | 地址 | 说明 |
|------|------|------|
| `sub_A126C5` | 0xA126C5 | 构造opcode 198拾取包并发送 |
| `sub_50D440` | 0x50D440 | 原生拾取遍历（Hook点） |
| `CDropPool` | - | 掉落池对象位置需从`CUserLocal`解析 |

## 路径对比分析（视觉渲染路径，与物品入包无关）

| 对照项 | 地面掉落路径 | 直达背包路径（视觉） |
|--------|-------------|-------------------|
| 关键函数 | `sub_60F2EF` → 创建地面实体 | `sub_50F9E2` → 直接创建 |
| 资源加载 | 加载mesh/贴图+1425 | 加载描述符+1426 |
| 可视化 | `sub_427EB3`(完整参数) | `sub_427EB3`(简化参数) |
| 安全性 | 有null-check → 清理退出 | 有null-check → 清理退出 |
| 异常 | SEH结构异常 | SEH结构异常(多检查dword_BE2788) |

> ⚠ 以上对比仅说明两条**视觉渲染路径**的差异，无论走哪条路径，**物品是否入包都由服务端决定**。NOP跳转只影响你看不看得到掉落在地面上。

## 崩溃风险评估表（针对+48分支NOP方案，仅视觉层面）

| 风险场景 | 概率 | 后果 | 说明 |
|---------|------|------|------|
| `sub_50F9E2` 返回空指针 | 低 | 安全退出 | `*(a1-40)` 检查后走清理路径 |
| `*v38` 解引用崩溃 | 极低 | 崩溃 | v38指向栈地址，不会为null |
| `dword_BE2788` 为零 | 低 | SEH异常 | 正常游戏中该全局变量非零 |
| `sub_427EB3` 返回null | 中 | 崩溃 | 但两条路径用同样参数调用，风险均等 |
| 服务端opcode 273 | 低 | 静默失败 | `DropItem_Remove` 查找不到实体后静默返回 |
| 数据包结构不同 | 无 | - | 分支前已全部解析，数据一致 |

**综合风险评级：★★☆☆☆（低-中）**。即使NOP掉跳转，崩溃风险也不高。但**需要再次强调：该方案不会让物品真的入包，只是改变了视觉表现**。
