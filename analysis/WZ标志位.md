# WZ 文件加壳标志位分析

## 来源

分析对象：第三方加密工具 V0.2（IDA Pro 反编译分析）

该工具号称"加密" WZ 文件，实际**不涉及任何加密运算**（无 AES/XOR/自定义密码）。也不解析 WZ 的目录属性树结构。仅通过一个**外壳级**的字节标志位来阻止某些 WZ 读取器（如开源 WZ Repacker）解析文件。

## 文件枚举

工具不递归解析 WZ 内部结构。它通过 `DirectoryInfo.GetFiles()` 枚举当前目录下的所有文件：

- 扩展名过滤：`.wz`
- 排除名单：`List.wz`、`Base.wz`
- 符合条件的文件逐一下处理

## 定位算法

此工具完全绕过了 WZ 文件的原生格式解析。它依赖一个**自定义的固定偏移约定**：

```
文件结构:
+0x00: 12 字节 WZ 文件头 (PKG1/PKG4 + 文件大小等) → 整体跳过，不解析
+0x0C: 4 字节 Int32 → 自定义定位值 S（非 WZ 原生字段，由本工具写入）
+0x10: ...文件数据...
+???: 其他数据...

定位流程:
1. BinaryReader.ReadBytes(12)         → 跳过 12 字节文件头
2. Int32 S = ReadInt32(offset=0x0C)   → 读取定位值 S
3. BinaryReader.ReadBytes(S - 17)     → 从当前位置(16)跳过 S-17 字节
4. 此时文件指针 = 16 + (S - 17) = S - 1
5. byte flag = ReadByte()             → 读取绝对偏移 S-1 处的标志位
```

**标志位的绝对文件偏移 = [偏移 0x0C 处的 4 字节 Int32 值] - 1**

## 判断与写入

| flag 值 | 含义 | 操作 |
|---------|------|------|
| `0x00` | 未加壳 | 用 BinaryWriter 寻址到 S-1，写入 `0x01` → "加壳成功" |
| `0x01` | 已加壳 | 跳过，输出"已经加壳了" |
| 其他值 | 异常 | 输出"读取失败" |

### 尺寸参数 S 的本质

S **并非 WZ 原生格式字段**。它是加壳工具**自己写入**的一个元数据值：

```
S = flag_byte_file_offset + 1
```

加壳工具在首次"包装"WZ 文件时，会在文件末尾追加 1 字节标志位，并将这个位置信息编码到偏移 0x0C 处。此工具对**未加壳的原生 WZ** 文件也能工作：读取 0x0C 处的值，如果该值指向文件末尾附近的一个零字节（原生 WZ 文件末尾自然为 `0x00`），则判定为"未加壳"并写入 `0x01`。

## 为什么 WZ Repacker 会失效

问题不在于末尾的 1 字节标志位，而在于：

1. **偏移 0x0C 被篡改** — WZ 原格式在 0x0C 位置有它的用途（可能是文件头的一部分或被解析引擎引用的字段），被这个工具覆盖为自定义值 S 后，WZ Repacker 读取到错误的值导致解析失败
2. **文件末尾追加 1 字节** — 多出 1 字节也可能破坏 Repacker 的文件边界检查

## 还原方法

### 方法一：修复标志位 + 0x0C 处原值

需要知道原始的 WZ 文件在 0x0C 处的值，然后：
1. 将 0x0C 处的 4 字节恢复为原始值
2. 将末尾标志位从 `0x01` 改回 `0x00`

### 方法二：对比加壳前/后差异

用 010 Editor / HxD 对比同一 WZ 文件加壳前和加壳后的二进制差异，直接找到被修改的两个位置。

### 方法三：写还原工具

```
1. 读取文件偏移 0x0C 处的 4 字节 → S
2. 检查偏移 S-1 处是否为 0x01
3. 如不修复 0x0C 处，仅把 S-1 处的 0x01 → 0x00
4. 有些 WZ Repacker 可能仅需恢复 0x0C 处就能工作
```

## 关键发现

| 项目 | 说明 |
|------|------|
| 加密算法 | 无（纯标志位翻转） |
| WZ 结构解析 | 不解析（不知道也不关心 WZ 的树结构） |
| 文件改动点 | 偏移 0x0C 写入 S + 文件末尾追加 1 字节标志位 |
| 标志位偏移 | `[0x0C 处的 Int32] - 1` |
| 定位方式 | 自定义元数据，非 WZ 原生结构 |
| 适用形态 | "外壳级"加壳标记 |

## 备注

- 这是 V0.2 版本的特性，后续版本可能引入了真正的加密算法
- 该标志位不影响 MapleStory 客户端本身读取 WZ 文件（客户端有独立的解析逻辑）
