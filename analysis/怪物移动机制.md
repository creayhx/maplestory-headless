# 怪物移动机制（Opcode 241 完整分析）

CMS 79 中怪物移动由服务端通过 **opcode 241** 控制。移动**不是**下发绝对坐标，而是下发一系列**增量**元素。

---

## 1. 关键结论

| 项目 | 结论 |
|------|------|
| 怪物坐标 | **全程加密存储**（ZtlSecure 系列加密），无法直接读写 |
| 怪物 body rect | `mob+0x3D4` 明文但每帧被加密坐标重算覆盖（只读） |
| 移动控制方 | **服务端权威**——路径/目标由服务端 opcode 241 下发 |
| 客户端本地AI | 存在（`CMob__UpdateAIAction`）但只处理**攻击决策**，不产生移动路径 |
| 增量值篡改 | 0x6B9044 Hook 改 `[edi+10]` 为 0 **无效** |
| 坐标加密范围 | 从服务端下发 → CMovePath 存储 → 物理读取，全程加密 |
| 明文坐标 | `mob+0x4C4/4C8` 为 int 坐标，**无CRC保护** |

---

## 2. 完整调用链路

```
服务端发送 opcode 241 (怪物移动包)
  ↓
CClientSocket → CField::OnPacket (0x541336)
  ↓
CMobPool::OnPacket (0x6A6AB0) → switch(opcode)
  ↓
CMobPool::OnMobPacket (0x6A6B0F) → case 241
  ↓
CMob::OnMove (0x69A483)  ← 主处理函数，ecx=怪物对象
  │
  ├── 1. 解码 move_type
  │     CInPacket::Decode1 → 原始字节
  │     ├─ move_type & 1  → mob+0xA8 (攻击标记)
  │     └─ move_type >> 1 → 类型分类:
  │         ├─ 12-20: 攻击移动 → CMob__ProcessAttackMove (0x69C432)
  │         ├─ 6-8:   特殊移动 → CMob__HandleAttackMove (0x693683)
  │         ├─ 21-37: 特殊效果 → 解码实体ID+音效
  │         └─ 其他: 普通移动 → 继续
  │
  ├── 2. 解码移动路径
  │     CInPacket::Decode4 → 路径数据
  │     sub_6B8DB5 (0x6B8DB5) ← 位置解密+写入
  │     │  ├─ DecryptEncodedDouble__cdecl ← 解密怪物位置
  │     │  └─ 写入 CMovePath+0x46/48/4A/4C 等偏移
  │     │
  │     CMovePath::OnMovePacket (0x6B8FB7)
  │       ├─ 保存旧状态
  │       ├─ 解密加密字段
  │       ├─ CMovePath::Decode (0x6B7F9A)
  │       │   └─ 从包中解析出移动元素链表
  │       ├─ 累加增量循环:
  │       │  for each 新元素:
  │       │    解密 this+0x8C(累计值) → 加元素[+0x10] → 加密存回
  │       ├─ 复制元素 → this+0x44 (20字节, qmemcpy)
  │       ├─ 计算移动定时
  │       └─ 超时(>5000ms) → 重置路径
  │
  └── 3. 收尾
        mov [esi+0x138] = 加密状态
```

### 本地 AI 更新循环

```
CMob__OnMobAttacked (vtable[1], 0x695DEE, 每帧/定时调用)
  ├─ CMob__UpdateTimers      — 更新定时器
  ├─ CMob__UpdateAIState     — AI状态机 (检查控制器, 150ms间隔)
  │   └─ 需要 CMob__IsController = 1 才执行
  ├─ CMob__UpdateAIAction    — AI决策 (读怪物←→玩家距离)
  │   ├─ 获取怪物位置: COM vtable[4] @ [mob+4]
  │   ├─ 获取玩家位置: COM vtable[4] @ [dword_BDD490+4]
  │   ├─ 计算距离 (abs + div)
  │   ├─ 距离 <= 40 (0x28): 调用 CMob__CheckMobAttackRange
  │   │   └─ 成功 → 调用 CMob__SendMobAttackPacket (opcode 189)
  │   └─ 否则: 继续
  └─ CMob__UpdateAIMovement  — 碰撞检测 + 发 opcode 188
```

### 后续帧驱动

```
每帧物理更新 (CPhysicalSpace2D?)
  └─ 读取 CMovePath 当前元素 (this+0x44):
      ├─ [+0x00] = 类型 (0=移动中, 3=结束)
      ├─ [+0x0C] = 移动速度
      ├─ [+0x10] = X 增量 (signed 16-bit)
      ├─ [+0x12] = Y 增量 (signed 16-bit)
      └─ [+0x14..] = 其他数据
      
      读取增量 → 加到怪物世界坐标 → 渲染新位置
```

## 4. CMovePath 结构

位于 `[mob+0x118] 子对象 + 0x19C` 处：

```
mov ebx, [esi+118h]          // 子对象指针
// 经过空指针调整后:
lea ecx, [ebx+19Ch]          // CMovePath 在此
call CMovePath::OnMovePacket
```

### 结构布局

| 偏移 | 大小 | 说明 |
|------|------|------|
| +0x00 | 4 | vtable 指针 |
| +0x04 | 4 | 加密值 |
| +0x08 | 4 | 加密值 |
| +0x0C | 4 | 加密值 |
| +0x10 | 4 | 子路径对象 |
| +0x18 | 4 | 元素计数器 |
| +0x20 | 4 | 当前元素指针 (链表) |
| +0x40 | 4 | 状态标志 |
| **+0x44** | **20** | **当前移动元素副本** ← 物理系统读取 |
| +0x46 | 2 | **怪物X？** (sub_6B8DB5 写入) |
| +0x48 | 2 | **怪物Y？** (sub_6B8DB5 写入) |
| +0x4A-0x5C | - | 其他值 |
| +0x5C-0x70 | - | 加密值 |
| +0x74-0x7C | - | 定时值 |
| **+0x8C-0x94** | **8+** | **累计移动量** (ZtlSecure 加密) |

### 当前移动元素 (this+0x44, 20字节)

```
偏移  大小  说明
+0x00  1    类型 (0=移动, 3=路径结束)
+0x01  1    ?
+0x02  2    ?
+0x04  4    ?
+0x08  2    ?
+0x0A  2    ?
+0x0C  2    移动速度/步长
+0x0E  2    ?
+0x10  2    X 方向增量 (signed 16-bit) ← 关键
+0x12  2    Y 方向增量 (signed 16-bit) ← 关键
```

> ⚠ `[edi+10]` 的值设为 0 后怪物仍正常移动，说明这个值可能不是移动增量，或是被其他机制覆盖了。

## 5. sub_6B8DB5 位置解密函数

从 `CMob::OnMove` 调用 (`0x69A561`, `0x69A5AB`)，解密加密坐标并写入 CMovePath：

```
sub_6B8DB5(this, a2, a3, a4)
  ├─ 如果 this+0x18(有路径): 处理路径中的位置元素
  │   └─ 更新 this+0x94 (加密累计值)
  │
  └─ 否则 (初始化路径):
      ├─ qmemcpy(v30, a3+8, 0x60)  ← 从 mob_field_data 复制加密数据
      ├─ DecryptEncodedDouble(v30)  ← 解密位置X
      ├─ mov [this+0x46], ax       ← 写入怪物X (16-bit)
      ├─ DecryptEncodedDouble(v30+6*4) ← 解密位置Y
      ├─ mov [this+0x48], ax       ← 写入怪物Y (16-bit)
      ├─ DecryptEncodedDouble(v30+12*4) ← 解密Z/方向
      ├─ mov [this+0x4A], di       ← 写入
      ├─ DecryptEncodedDouble(v30+18*4) ← 解密另一个值
      ├─ mov [this+0x4C], di       ← 写入
      ├─ ZtlSecureTear 加密存回 this+0x64/0x70
      ├─ ...清理旧路径...
      └─ 重置累计值
```

**关键发现**：`CMovePath+0x46` 和 `+0x48` 是**怪物解密后的明文位置**(16-bit)！但随后被 ZtlSecure 加密存回 `+0x64/0x70`，真正的明文位置只短暂存在。

## 6. 怪物坐标存储

### 入场初始化 (sub_690E09)

```
mob+0x4C4    X (int 坐标)          ← 无CRC保护
mob+0x4C8    Y (int 坐标)          ← 无CRC保护
mob+0x4CC    X (short 副本)        ← 无CRC保护
mob+0x4D0    Y (short 副本)        ← 无CRC保护
```

```asm
; sub_690E09 反汇编
call  CInpacket__Decode2        ; X (short)
movsx eax, ax
mov   [ebx+4CCh], eax           ; mob+0x4CC = X short
call  CInpacket__Decode2        ; Y (short)  
movsx eax, ax
mov   [ebx+4D0h], eax           ; mob+0x4D0 = Y short
; 复制到int副本
mov   eax, [ebx+4CCh]
mov   [ebx+4C4h], eax           ; mob+0x4C4 = X int
mov   eax, [ebx+4D0h]
mov   [ebx+4C8h], eax           ; mob+0x4C8 = Y int
```

### CPhysical 子对象位置

```
mob+0x178 → CPhysical子对象
  +0x0C       Foothold/物理系统数据
  +0x14       同上
  +0x40       ZtlSecureFuse保护的位置值（+0x48是校验值）
  +0x4C       ZtlSecureFuse保护的int（+0x54是校验值）
  +0x194      ZtlSecureFuse保护的值（+0x19C是校验值）
  +0x1C8      ZtlSecureFuse保护的值（+0x1D0是校验值）
  +0x208      HP/Boss血条标志
  +0x21C      目标列表/技能列表
```

### 坐标来源总结

| 线索 | 来源 | 说明 |
|------|------|------|
| `mob+0x4C4/4C8` | `GetBodyRect` 中的 `this[305/306]` | 传递给 `dword_BE1704` 用作坐标偏移 |
| `mob+0x3D4-0x3E0` | `GetBodyRect` 中的 body rect | 左右上下四个边界值 |
| `CMovePath + 0x44` | 当前移动元素 | 增量值在此，物理系统读取后累加 |
| 累计值 `CMovePath + 0x8C` | 解密后累加 | ZtlSecure 加密存储 |

最可能的情况：怪物世界坐标由 `CMovePath` 的累计值 + 初始偏移计算得出，存储位置可能是 `mob+0x4C4/4C8` 或通过 COM 接口间接访问。

## 7. 增量式移动的理解

怪物移动**不是**服务端下发绝对坐标，而是下发一系列**增量**：

```
服务端: "怪物向左走5像素"
  → 包中包含元素: {x_delta=-5, y_delta=0}
  → 累加: 累计X += (-5)
  → 怪物新位置 = 旧位置 + (-5, 0)

服务端: "怪物向右走10像素, 向上走3像素"
  → 包中包含元素: {x_delta=+10, y_delta=-3}
  → 累加: 累计X += 10, 累计Y += -3
```

### 包中的典型元素序列

一个 opcode 241 包通常包含**多个移动元素**，形成一条路径：

```
元素1: {type=0, x_delta=+50, y_delta=0}   → 向右走50
元素2: {type=0, x_delta=0,  y_delta=-30}  → 向上走30
元素3: {type=0, x_delta=+20, y_delta=+10} → 向右20, 向下10
元素4: {type=3}                            → 路径结束
```

## 8. 增量篡改方案分析

### 方案A：在 CMovePath::OnMovePacket 中篡改增量

**位置**：`CMovePath::OnMovePacket` (0x6B8FB7) 的增量累加循环中

```
关键代码 (0x6B9044):
  movsx ecx, word ptr [edi+10h]  ; 从元素读 X 增量 (signed 16-bit)
  add ecx, eax                    ; 加到累计值
  ... 
  movsx ecx, word ptr [edi+12h]  ; 从元素读 Y 增量
```

**修改思路**：Hook 这个累加点，把增量值改成指向玩家方向。

**结果**：❌ 无效。`[edi+10]` 的值设为 0 后怪物仍正常移动。

### 方案B：在 CMovePath + 0x44 副本上篡改

**位置**：累加循环结束后，`qmemcpy(this+0x44, ...)` 已复制当前元素副本。

**修改思路**：在 OnMovePacket 末尾（0x6B9037 返回前），修改 `this+0x44` 处的增量值。

### 方案C：Hook 物理帧读取点

**思路**：找到物理引擎每帧从 `CMovePath+0x44` 读取增量的位置，在那里做篡改。

### 方案D：直接写怪物世界坐标（吸怪/瞬移）

**位置**：`CMob::OnMove` 末尾或定时器写入 `mob+0x4C4/4C8`

## 9. 怪物移动/传送实现方案

### 方案一：内存直接写坐标（推荐入门）

修改 `mob+0x4C4`（X）和 `mob+0x4C8`（Y），**无 CRC 保护**。

**步骤：**
1. 定位怪物池指针 `CMobPool*`（全局地址：`0xBDD49C`）
2. 从怪物池中遍历所有怪物（链表 `this+0x28`）
3. 对每个怪物写入目标坐标
4. 需要定时重复执行（如每 50~100ms），防止被服务端包覆盖

**优点：**
- 实现简单，直接内存操作
- 不触发CRC保护

**缺点：**
- 坐标被游戏物理引擎刷新后会恢复
- 怪物正在移动时会被移动包覆盖
- 需要定时执行才能保持

### 方案二：利用游戏自身移动系统

调用 `sub_6B8DB5`（移动路径处理函数）或直接操作 `CMovePath` 让怪物平滑移动。

```
void TeleportMobToPlayer(CMob* mob, int targetX, int targetY) {
    // 1. 获取或创建移动路径
    // 2. 填入目标坐标
    // 3. 调用移动处理函数 sub_6B8DB5
    // 游戏会自己处理CRC更新
}
```

**优点：** 游戏自身处理CRC，完全合法，怪物平滑移动
**缺点：** 需要理解移动包完整构造，实现复杂

### 方案三：CPhysical 子对象坐标同步

除了写 `mob+0x4C4`，同步更新 `mob+0x178` 指向的子对象内的位置数据：

```asm
mov eax, [esi+178h]          ; CPhysical子对象
test eax, eax
jz skip_sync
mov [eax+0x??], NEW_X        ; 需要找到子对象的坐标偏移
mov [eax+0x??], NEW_Y
skip_sync:
```

子对象 `+0x40` 有 ZtlSecureFuse 保护，但 `+0x00~+0x3C` 范围可能有未保护的坐标字段。

## 10. 吸怪绕 CRC 原理

### CRC 不保护的内容

- **怪物的 X/Y 坐标值**（mob+0x4C4~+0x4D0）→ **无保护**
- 移动数据包的解析和发送过程 → **无保护**
- `CMovePath` 移动路径对象 → **无保护**

### 包级别吸怪原理（推荐方式）

```
Hook CClientSocket::SendPacket (或特定opcode)
  ↓
拦截发往服务端的移动数据包
  ↓
修改包中的目标坐标 → 指向玩家位置
  ↓
服务端收到后认为玩家在移动
  ↓
服务端更新怪物AI → 怪物向玩家移动
  ↓
CMob::OnMove 正常处理 → CRC自动正确更新，不触发校验
```

因为不修改客户端本地的 CRC 保护内存，所以**完全不会触发 CRC 校验**。

### 内存级别吸怪注意事项

直接写 `mob+0x4C4` / `mob+0x4C8` 坐标时：
- **不会触发 CRC 校验**（这些字段无保护）
- 但可能被服务端下发的下一帧移动包覆盖（需要持续写入）
- 渲染位置可能仍从 CPhysical 子对象读取，需要同步更新

## 11. 崩溃风险评估

| 风险场景 | 概率 | 后果 | 说明 |
|---------|------|------|------|
| 写入非法坐标值 | 低 | 怪物瞬移/穿墙 | 游戏有Foothold碰撞检测，不合理坐标会被纠正 |
| 怪物链表遍历异常 | 低 | 崩溃 | 需正确处理空指针和链表结构 |
| CRC校验触发 | 极低 | C++异常 | 直接写mob+0x4C4不触发CRC |
| 服务端位置修正 | 中 | 怪物跳回原位 | 服务端定期下发位置同步包 |
| 同步更新CPhysical子对象 | 中 | 显示异常 | 渲染引擎从子对象读位置时未同步 |

### 关键建议

- **先用方案一做POC**，直接在CE中验证写坐标是否生效
- 观察是否被服务端修正，如果修正则配合**包拦截**（拦截位置同步包）
- 如需持久效果，使用**定时器**每帧写入
- 后续可升级到方案二，实现更平滑自然的怪物拉取效果

## 13. 怪物移动诱导（方案五：opcode 241 坐标篡改）

**对应 CT 文件：** `怪物自动跟随.CT` → 怪物移动诱导 v1

### 原理

服务端下发 `opcode 241`（怪物移动包）时，客户端通过 `CMob::OnMove`（`0x69A483`）处理。在 `CMovePath::OnMovePacket` 解析完移动路径后，`CMob::OnMove` 末尾（`0x69A814`）将怪物坐标改写为玩家坐标。

```
服务端 → opcode 241 (怪物路径) → CMob::OnMove
  → CMovePath::OnMovePacket (解析路径)
  → Hook 在函数末尾: [esi+4C4/4C8] = 玩家坐标
  → 怪物渲染在玩家附近
```

### 数据依赖

| 数据 | 来源 | 偏移 |
|------|------|------|
| 玩家对象基址 | `dword_BDD490` | `[0xBDD490]` |
| 玩家 X | 人物位置文档 | `+0x28F8` |
| 玩家 Y | 人物位置文档 | `+0x28FC` |
| 怪物 X | `GetBodyRect` 分析 | `mob+0x4C4` |
| 怪物 Y | `GetBodyRect` 分析 | `mob+0x4C8` |

### 推荐实现路径

1. **第一步：确定怪物世界坐标偏移** — 在 CE 中验证 `mob+0x4C4/4C8` 的实际效果
2. **第二步：实现增量诱导** — 修改 `CMovePath` 的增量值
3. **第三步：针对所有怪物** — 遍历怪物池
