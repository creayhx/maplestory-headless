## 数据结构

### CReactorPool (全局池，ptr at 0x00BDEB38)

```
+0x00: vtable
+0x08: dword  reactor 数量 (31 = 31个)
+0x18: 碰撞入口表 (vtable，sub_743100 使用索引查询)
+0x24: ptr   实体数组 begin (32 字节/条目，[entry+4]=实体指针)
+0x28: ptr   实体数组 end
```

池和实体在放置物重生时会被 free 并重新分配，全局指针 [0x00BDEB38] 同步更新。

`sub_743100(ecx=pool+0x18, index)` → 返回碰撞条目指针 (下称 CollisionEntry)

### 实体数组 (pool+0x24 ~ pool+0x28)

每个条目 32 字节：

```
+0x00: dword  未知 (一般为 0)
+0x04: ptr    CReactorEntity*
+0x08: dword  24 (常量)
+0x0C: ptr    vtable (0x00B05D04)
+0x10: ptr    自身地址
+0x14: ptr    前一条目地址
+0x18: ptr    vtable (0x00B05D00)
+0x1C: dword  0
```

数组遍历：从 begin 到 end，步长 0x20 (32)，取 [entry+4] 得实体指针。

### CReactorPool (完整结构)

```
+0x00: ptr    vtable (0x00B0DB34)
+0x04: ptr    源信息指针 (reactor meta info table)
+0x08: dword  总 reactor 数量 (含未刷新的)
+0x0C: dword  当前活动 reactor 数量 (与 CollisionEntry 表一致)
+0x10: dword  100 (常量)
+0x14: dword  24 (常量)
+0x18: struct CCollisionEntryTable (嵌套对象)
│  +0x00: ptr  vtable (0x00B0DB30)
│  +0x04: ptr  数据数组 (0x00AFE644, 静态分配的索引表)
│  +0x08: dword 活动条目数 (同 pool+0x0C)
│  +0x0C: ptr  正向遍历起始指针 (linked list head)
│  +0x10: ptr  反向遍历起始指针 (linked list tail)
+0x24: ptr    实体数组 begin (32 字节/条目)
+0x28: ptr    实体数组 end
+0x2C: dword  60 (常量)
+0x30: ptr    (指针)
```

池和实体在放置物重生时会被 free 并重新分配，全局指针 [0x00BDEB38] 同步更新。

### CollisionEntry (完整字段，由三个 packet handler 逆向验证)

`sub_743100(ecx=pool+0x18, index)` → 返回 wrapper_ptr → [wrapper_ptr+4] = CollisionEntry*

```
+0x00: dword  reactor_id      (包中第一个字段, Decode4)
+0x04: dword  template_id     (Wz 数据表外键, NOT 指针！)
+0x08: ptr    skill_table     (技能表, NULL=无技能检查直接发包)
+0x0C: dword  prev_state      (旧状态, LeaveField/ChangeState 时备份)
+0x10: dword  state           (当前状态, Decode1 更新)
+0x14: word   pos_x           (X坐标, signed, 地图坐标)
+0x18: word   pos_y           (Y坐标, signed, 地图坐标)
+0x1A~0x23: 未知填充
+0x24: dword  field_0x24      (多重含义: TryHit=-2, ChangeState=动作类型, Leave=-2)
+0x28: dword  timeout         (冷却截止时间戳, 各种 handler 都会更新)
+0x2C: dword  field_0x2C      (动画时间戳? Leave 不变, Change=time+count×100)
+0x30: dword  field_0x30      (多重含义: 0=活跃, 1=已击打/已进入, 4=已离开)
+0x34: dword  hit_type        (TryHit 时由玩家属性计算)
+0x38: ptr    com_iface       (COM 事件接口, EnterField 时创建)
+0x3C: ptr    wz_vector2d     (COM 坐标对象, EnterField 时挂载)
+0x40: dword  visible_flag    (0=隐藏, 1=可见, EnterField 时从包读取)
+0x44: ptr    (未知)
+0x48: dword  0x58 (常量?)
```

### sub_743100 链表遍历算法

sub_743100 内部维护了一个双向链表结构：

```c
// ecx = pool+0x18 (CCollisionEntryTable)
int* __thiscall sub_743100(int* this, unsigned int index) {
    if (index <= this[2] >> 1) {        // index <= count/2
        result = this[3];               // 正向起始指针
        for (i = 0; i < index; i++)
            result = [result-12] ? [result-12]+16 : 0;  // 正向遍历
    } else {
        result = this[4];               // 反向起始指针
        for (j = this[2]-1; j > index; j--)
            result = [result-8] ? [result-8]+16 : 0;    // 反向遍历
    }
    return result;                      // wrapper_ptr, [wrapper+4] = CollisionEntry*
}
```

每个链表节点 16 字节，节点间通过 `[ptr-12]` 和 `[ptr-8]` 连接。

### pool+0x24 实体数组 (备选数据源，不推荐)

```
+0x00: dword  未知 (一般为 0)
+0x04: ptr    CReactorEntity*  (注意：这是实体指针，不是 CollisionEntry!)
+0x08: dword  24 (常量)
+0x0C: ptr    vtable (0x00B05D04)
+0x10: ptr    自身地址
+0x14: ptr    前一条目地址
+0x18: ptr    vtable (0x00B05D00)
+0x1C: dword  0
```

**注意**：该数组只有 2 个有效实体，其余条目为空或指向 vtable。
**CollisionEntry 链表才是正确的数据源**，包含全部活动 reactor。

│
├─ ★ 阶段一：可视化碰撞环遍历 (0x7422C6 - 0x742373)

│   │   对每个实体：
│   │   ├─ [0x7422E4] entity = [entry+4]
│   │   ├─ [0x742310] cmp [eax+0x30], ebx   ← hit_flag == 0?
│   │   │   └─ jnz → skip (已被击打过)
│   │   ├─ [0x742318] sub ecx, [eax+0x2C]   ← 动画冷却到期?
│   │   │   └─ js → skip (冷却未结束)
│   │   └─ [0x742327] call sub_747258        ← COM 碰撞检测

│   │   [0x742379] call sub_962A51(player, &ZArray, &delay, 1)
│   │   ├─ 返回 reactor 索引 (>=0) → 碰撞命中
│   │   └─ 返回 -1 → 无碰撞，跳过
│   │   [0x7423A4] cmp eax, ebx → jl 0x742697 (exit)
│   │
│   └─ [0x7423AC-0x7423BB] 解析碰撞条目
│       push eax (index)
│       mov ecx, [edi+0x18]  (pool+0x18)
│       call sub_743100       → 返回 CollisionEntry* 存入 [ebp-34]
│       [0x7423BE] call sub_742D5D  (AddRefReactor)
│
├─ ★ 阶段三：技能检查 (0x742542)
│   │   [0x742542] mov ecx, [eax+0x08]  ← entry->skill_table
│   │   [0x742547] cmp ecx, ebx
│   │   └─ je 0x7425D1  → skill_table==NULL，跳过技能检查
│   │
│   ├─ [skill_table != NULL] 复杂技能检查和循环 (0x74254D-0x7425CE)
│   │   ├─ 验证技能表有效
│   │   ├─ 遍历技能条目匹配当前攻击技能
│   │   └─ 匹配失败 → ReleaseReactor + exit (0x742697)
│   │
│   └─ [skill_table == NULL] → jmp 0x7425D1  (快速路径)
│
├─ ★ 阶段四：发包准备 (0x7425D1 - 0x742624)
│   │   注意：eax 在此路径上由 [0x7423C3] 从 [ebp-34] 加载
│   │
│   ├─ [0x7425D1] push 01 / pop edi     ← edi = 1
│   ├─ [0x7425D4] mov [eax+0x30], edi    ← entry->hit_flag = 1
│   ├─ [0x7425D7-0x7425FD] 从 esi (player) 计算 hit_type
│   ├─ [0x742602] mov [eax+0x34], ecx    ← entry->hit_type = 计算值
│   ├─ [0x742605] mov esi, [ebp-34]      ← esi = entry
│   ├─ [0x742608] call sub_994C7A         ← 获取当前时间
│   ├─ [0x74260D] add eax, [ebp-1C]      ← + delay
│   ├─ [0x742615] mov [esi+0x28], eax    ← entry->cooldown = cur_time + delay
│   ├─ [0x742618] mov eax, [ebp-34]      ← eax = entry
│   ├─ [0x74261B] lea ecx, [ebp-58]      ← ecx = COutPacket 缓冲区
│   └─ [0x74261E] mov dword [eax+0x24], 0xFFFFFFFE ← event_type = -2
│
├─ ★ 阶段五：构建 COutPacket(0xC9) (0x742625)
│   │   [0x742625] call 0x6F5E40         ← COutPacket::COutPacket_2(0xC9)
│   │
│   ├─ [0x74262D] push [eax]             ← reactor_id (entry+0x00)
│   │   [0x742632] call 0x40667C         ← Encode4(reactor_id)
│   │
│   ├─ [0x742636] push ebx               ← 0
│   │   [0x74263F] call 0x40667C         ← Encode4(0)
│   │
│   ├─ [0x742647] push [eax+0x34]        ← hit_type (entry+0x34)
│   │   [0x74264D] call 0x40667C         ← Encode4(hit_type)
│   │
│   ├─ [0x742652] push [ebp-1C]          ← delay
│   │   [0x742658] call 0x4291B3         ← Encode4(delay)

│   ├─ [0x742660] push ebx               ← 0

## 冷却绕过方案

### 原理

TryHitReactor 的可视化环遍历阶段有两道跳过检查：

| 地址 | 指令 | 含义 | 绕过 |
|------|------|------|------|
| 0x742313 | `jnz 0x742365` | `entity+0x30 != 0` 时跳过 | NOP: `90 90` |
| 0x74231B | `js 0x742365` | 动画计时器未到期时跳过 | NOP: `90 90` |

NOP 掉这两个跳转后，所有 reactor 始终进入 COM 碰撞检测。**但注意**：这只是可视化环的检查，实际的发包逻辑由 stage 2 的 sub_962A51 控制，因此仅 NOP 此处还不够——还需要让 sub_962A51 返回有效索引。

## 总览：三个 Packet Handler 对比

| | OnReactorEnterField (286) | OnReactorChangeState (284) | OnReactorLeaveField (287) |
|------|---------------------------|---------------------------|---------------------------|
| **语义** | 放置物进入/刷新地图 | 放置物状态变化 | 放置物离开地图 |
| **数据流** | 服务端→客户端 | 服务端→客户端 | 服务端→客户端 |

## OnReactorLeaveField (0x7420ec) — 放置物离开

### 基本信息

| 属性 | 值 |
|------|------|
| 地址 | `0x7420ec` |
| 大小 | `0x1a8` (424 字节) |
| 调用约定 | `__userpurge` (ebp 帧, ecx = pool this) |
| 触发条件 | 服务端发送 packet **header 287 (0x011F)** |
| 分发点 | `CReactorPool::OnPacket` (0x741C0B) → header==287 |

### 包结构

| 序号 | 类型 | 字段 | 说明 |
|------|------|------|------|
| 1 | Decode4 | reactor_id | 离开的放置物 ID |

### 完整执行流程

```
OnReactorLeaveField(ecx=pool)
│
├─ [0x742103] Decode4(packet) → reactor_id
│
├─ [0x74211D] sub_742E04(pool.hash_table, reactor_id, lock=true)
│   ├─ 未找到 → 清理临时对象 (sub_742D7A), return
│   └─ 找到 → entry 指针 (引用计数已递增)
│
└─ ★ 找到 reactor，进入更新流程

    ├─ [0x74213C] update_time = get_update_time()
    │
    ├─ ★ 更新字段 (来自 packet)
    │   ├─ [0x742145] entry->prev_state = entry->state  (保存旧状态)
    │   ├─ [0x74214B] entry->state      = Decode1()     (新状态, 1byte)
    │   ├─ [0x74215B] entry->pos_x      = Decode2()     (X坐标, 2byte)
    │   └─ [0x74216B] entry->pos_y      = Decode2()     (Y坐标, 2byte)
    │
    ├─ ★ COM 事件通知
    │   ├─ [0x742181] 构造 VARIANT(reactor_id)
    │   ├─ [0x74218E] 构造 VARIANT(state/pos)
    │   ├─ [0x7421CC] call entry->vtable[0x110](entry, 0, variant1, variant2)
    │   └─ [0x7421FA] 释放 VARIANT (COM 清理)
    │
    ├─ ★ 标记为"已离开"
    │   ├─ [0x742215] entry->field_0x30 = 4     (状态标记)
    │   ├─ [0x742229] sub_747258(pool, tmp, entry->state)
    │   │             查找关联对象 → 判断是否需要冷却
    │   ├─ [0x742244] timeout = update_time + 400 (约4秒)
    │   │             特殊情况: update_time==-400 → timeout=1
    │   ├─ [0x742253] entry->field_0x28 = timeout (超时时间戳)
    │   └─ [0x74226E] entry->field_0x24 = -2    (离开标记 0xFFFFFFFE)
    │
    └─ ★ 清理
        ├─ [0x74225F] 清理临时关联对象 (sub_742DD5)
        └─ [0x74227E] sub_742DA6 — 递减 reactor 引用计数
                      如果归零 → 析构释放对象
```

### 更新后的 Entry 字段

| 偏移 | 字段 | 离开后的值 |
|------|------|-----------|
| +0x0C | prev_state | 旧 state (复制前) |
| +0x10 | state | 新 state (来自 packet, 通常为 0?) |
| +0x14 | pos_x | 新 X (来自 packet) |
| +0x18 | pos_y | 新 Y (来自 packet) |
| +0x24 | field_0x24 | **-2 (0xFFFFFFFE)** |
| +0x28 | field_0x28 | update_time + 400 (超时≈4s) |
| +0x30 | field_0x30 | **4 (已离开)** |

### 关键设计要点

**不主动删除，只做标记。** 该函数不直接从池中移除 reactor 条目，只是将 `[entry+0x24]` 和 `[entry+0x30]` 设为特定值标记"已离开"。条目仍然在哈希表中，pool+0x08（总数量）不变。

**被动的服务端通知。** 这是纯粹的服务端→客户端的通知包，客户端被动响应。与 `TryHitReactor` (主动发包击打) 是相反的数据流向。

**与碰撞表的关系。** CollisionEntry 链表 (`pool+0x18`) 字段也会在离开时更新，但 `pool+0x0C`（活跃数量）和 `pool+0x20`（碰撞表 count）会在离开时递减。这是我们之前选择 `pool+0x08`（总数量）作为循环计数更稳定的原因：条目不被删除，计数不变化。

### 基本信息

    ├─ [0x741C8B] entry->prev_state = entry->state (备份旧状态)

| 方面 | OnReactorChangeState (284) | OnReactorLeaveField (287) |

## 实验记录

### 普攻空地图触发 (no-collision forced send)

Hook 点：`0x7423A4`，截获 sub_962A51 返回 -1（无碰撞）时。

脚本逻辑：当碰撞返回 -1 时，遍历链表 `[pool+0x24]` → `[entry+4]` 取第一个 entity，构造 COutPacket(0xC9) 强制发送。

- 发包成功（服务端收到）
- 但 reactor 不一定会被击打——服务端有自己的碰撞/状态校验
- 不会崩客户端，普攻动画正常

### state 修改实验

Hook 点：`0x7423C6`，在 CollisionEntry 非空时将 `entry+0x24` 强制设为 3 或 4。

- 设 3：攻击 2 次后 reactor 破坏（与正常行为无差异）
- 设 4：无效，服务端不承认
- 结论：服务端对 state 有独立校验，客户端写入不影响服务端判定

### 最终方案：CoordMove 全图攻击

#### 原理

在 `TryHitReactor` 的碰撞检测阶段前（0x74238D），Hook `mov esi, [00BDD490]` 指令。

通过 `call sub_743100` 遍历 **CollisionEntry** 链表获取所有活动 reactor 的正确坐标，将玩家人物瞬移到 reactor 左侧 + 同一高度，使 `sub_962A51` 碰撞检测必然命中。

**关键点：**
- 必须使用 `sub_743100` 获取 CollisionEntry（pool+0x24 数组数据错误）
- count 从 `pool+0x0C` 读取（活动数量，不是 pool+0x08 的总数）
- **同时修改 X 和 Y**：只改 X 只能打到同一行的，加 Y 后全图覆盖
- 地图切换检测：pool+0x0C 变化时自动重置索引
- 后置钩子在函数退出时还原玩家原始坐标

#### 地址速查（新增）

| 用途 | 地址/偏移 | 说明 |
|------|----------|------|
| 活动 Reactor 数量 | pool+0x0C | 和 CollisionEntry 表一致 |
| 总 Reactor 数量 | pool+0x08 | 含未刷新的 |
| 碰撞表 count | pool+0x18+0x08 = pool+0x20 | sub_743100 内部使用 |
| 正向遍历起始 | pool+0x18+0x0C | 链表头 |
| 玩家 X 偏移 | player+0xee8 | 4 字节 |
| 玩家 Y 偏移 | player+0xeec | 4 字节 |
| PreHook | 0x74238D | 替换 `mov esi,[00BDD490]` |
| PostHook | 0x742697 | 替换 `or [ebp-4],-1; lea ecx,[ebp-10]` |

### 进阶方案：ChainTrigger 连锁触发（一次攻击全图清场）

#### 原理

在 CoordMove 后置钩子（PostHook 0x742697）中，恢复玩家坐标后自动触发循环，依次调用 `TryHitReactor` 击打剩余的所有活动放置物。

**执行流程：**

```
游戏攻击 → TryHitReactor (第1次)
  ├─ PreHook:  保存坐标 → 移动到 reactor[0] 左侧
  ├─ Body:     sub_962A51 碰撞 → 发包击打 reactor[0]
  └─ PostHook: 恢复原始坐标
       └─ 连锁循环 (chain_active=1):
            ├── 调用 TryHitReactor(reactor[1])
            │    ├─ PreHook: chain_active==1 → 跳过 (不保存/不移动)
            │    ├─ Body: 碰撞命中 reactor[1] → 发包
            │    └─ PostHook: chain_active==1 → 跳过后置逻辑
            │
            ├── 调用 TryHitReactor(reactor[2])
            │    └─ (同上)
            │
            ├── ...reactor[3..n-1]...
            │
            └── 连锁结束
                ├─ 恢复原始坐标
                └─ chain_active=0
```

#### 关键设计

| 组件 | 行为 |
|------|------|
| `chain_active` 标志 | 位于 `CoordCave+0x3B8`，连锁期间置 1 |
| **PreHook 检查** | chain_active==1 → 跳过所有 save/modify 逻辑，仅 `mov esi,[00BDD490]; jmp 返回` |
| **PostHook 检查** | chain_active==1 → 跳过自身恢复逻辑，也跳过连锁触发逻辑，直接回原始流程 |
| **永久保存槽** | CoordCave+0x3AC/0x3B0/0x3B4：保存玩家指针/X/Y，连锁期间不会被 PreHook 覆盖 |
| **循环方式** | 在 PostHook 中用 `call 00742294` 直接调用 TryHitReactor，循环而非递归，stack 深度安全 |
| **终止条件** | 索引 >= 活动数量（pool+0x0C - 1）时自然退出 |

#### 与旧方案的关键区别

| 方面 | v2 (CoordMove) | v3 (ChainTrigger) |
|------|----------------|-------------------|
| 每次攻击击打 | 1 个 | **全部活动放置物** |
| 是否需要反复攻击 | 需要（轮换） | **原地一次普攻** |
| 服务端检测风险 | 低（自然攻击流程） | 同左（每次调用都是完整自然流程） |
| chain_active 保护 | 无 | 防止递归死循环 |

#### 新增地址速查

| 用途 | 地址/偏移 | 说明 |
|------|----------|------|
| chain 永久玩家指针 | CoordCave+0x3AC | 连锁期间不会变 |
| chain 永久 X 保存 | CoordCave+0x3B0 | 用于最后恢复 |
| chain 永久 Y 保存 | CoordCave+0x3B4 | 同上 |
| chain_active 标志 | CoordCave+0x3B8 | 0=正常, 1=连锁中 |

### 最终方案：并发攻击 (PostHook 循环并发)

#### 原理

在 `TryHitReactor` 的 PostHook (0x742697) 中，恢复玩家坐标后通过循环依次调用 `TryHitReactor`，实现一次攻击多次命中。

**核心改进：** 用 `chain_active` 一次性锁住整个并发区间，嵌套的 PostHook 直接跳过，从根本上杜绝了递归死循环。

#### 执行流程

```
1次攻击 → TryHitReactor (第1次)
  ├─ PreHook:  保存坐标 → 移动玩家到 reactor[N]
  ├─ Body:     sub_962A51 碰撞 → 发包击打 reactor[N]
  └─ PostHook: 恢复原始坐标
       └─ chain_active=1 锁住
            ├── call TryHitReactor (第2次) → PreHook(advance) → Body(hit) → PostHook(skip)
            ├── call TryHitReactor (第3次) → PreHook(advance) → Body(hit) → PostHook(skip)
            ├── ...
            └── call TryHitReactor (第N次) → PreHook(advance) → Body(hit) → PostHook(skip)
       └─ chain_active=0 解锁 → 返回游戏
```

#### 关键设计

| 组件 | 说明 |
|------|------|
| `chain_active` (0x3B8) | 并发锁，PostHook 入口先检查，已锁则直接跳过 |
| 锁定时机 | 在首次 PostHook 中设置 `chain_active=1` 后，立即进入循环 |
| 解锁时机 | 循环结束后清 `chain_active=0` |
| 循环体 | 直接用 `call 00742294` 调用 TryHitReactor，完整走 PreHook→Body→PostHook |
| 嵌套安全 | 嵌套的 PostHook 看到 `chain_active=1` 直接跳到 epilogue，不触发额外调用 |
| 索引旋转 | PreHook (CoordCave) 每次调用都会推进索引，确保轮询所有 reactor |
| 索引边界 | 使用 `CoordCave+0x3CC` 固定保存首次调用的活跃数，防止执行中数量收缩导致越界 |
| 越界保护 | `cmp ebx, [edx+0x0C]; jae CoordNo` 确保仅处理有效索引 |

#### CoordCave 内存布局 (0x400 bytes)

| 偏移 | 用途 | 说明 |
|------|------|------|
| +0x384 | 保存的原始 X | 用于 PostHook 恢复玩家坐标 |
| +0x388 | 保存的玩家指针 | 确保坐标写回正确的对象 |
| +0x38C | 修改标志 (0/1) | PreHook 是否移动了玩家，PostHook 据此决定是否恢复 |
| +0x394 | 保存的原始 Y | 同 X |
| +0x3A4 | 当前 reactor 索引 | 每次 PreHook 递增，轮询所有活动 reactor |
| +0x3B8 | chain_active (1 byte) | 并发锁，0=正常, 1=并发中 |
| +0x3CC | 固定活跃数 | 首次 PreHook 从 pool+0x0C 保存，作为索引模数 |
| +0x3D4 | 命中计数器 | 每次 PreHook 成功移动玩家时递增 |


#### 并发数切换

| 模式 | 操作 |
|------|------|
| **自动 (默认)** | `mov eax,[00BDEB38]` + `mov ebx,[eax+0x08]` — 读取 pool+0x08 (地图总放置物数量) |
| **手动** | 注释掉上面两行，取消注释 `mov ebx, N`，改 N 为想要的数值 |

#### 与 ChainTrigger 的区别

| 方面 | ChainTrigger (旧) | 并发攻击 (新) |
|------|-------------------|---------------|
| 调用位置 | PostHook 直接循环 | PostHook 循环，但 `chain_active` 一次性锁定 |
| 嵌套保护 | PreHook 检查标志跳过 | **PostHook 检查标志跳过**，直接到 epilogue |
| 索引边界 | 使用实时 pool+0x0C | 使用 `0x3CC` 固定保存值，防止执行中收缩 |
| PreHook 行为 | chain_active 时跳过 | **永不跳过**，始终推进索引并移动玩家 |
| 适用场景 | 一次攻击清全图 | 持续攻击高并发覆盖，可调并发数 |
| 状态风险 | 坐标频繁变动导致攻击动画失效 | 同左 (本质限制) |

### 关于直接发包方案的说明

旧方案（不经过 TryHitReactor，直接构造 COutPacket(0xC9) 发送）所以无效的原因分析：

1. **缺少碰撞上下文：** 服务端收到的 0xC9 包需要与客户端的碰撞状态匹配。旧方案跳过了 `sub_962A51`，发包中的 hit_type、delay 等字段由玩家属性计算，但服务端可能额外校验碰撞状态
2. **无需服务端范围检测：** 当前 ChainTrigger 方案走完整 TryHitReactor 流程，sub_962A51 基于实际坐标做碰撞判断，通过瞬移玩家到放置物旁边来"欺骗"碰撞检测，服务端收到的是正常流程产生的包，不存在范围检测绕过的问题
3. **扩展思考：** 如果未来想实现在不移动坐标的情况下直接触发，可以考虑 Hook `sub_962A51` 直接返回期望的索引，但这需要更深入分析该函数的状态维护逻辑
